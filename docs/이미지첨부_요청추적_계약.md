# 이미지 첨부·에이전트 이미지 공유·참가자 간 요청 계약 (v1.1)

2026-10-19 설계 방(Astra·Argon) 제안과 오케스트레이터 결정을 묶은 구현 계약이다. 구현은 이 문서의 이름을 그대로 쓴다. 계약을 바꿔야 하면 먼저 방에 알린다.

## 1. 결정

| 번호 | 결정 |
| --- | --- |
| E1 | "모두 볼 수 있다"는 모든 참가자가 **다음 발언 때** 첨부를 받는다는 뜻이다. 첨부만으로 턴을 새로 실행하지 않는다. 기존 `cap`·`LastSeen`·`Unseen` 경계로 새 첨부만 한 번 전달한다. |
| E2 | 형식은 PNG·JPEG·WEBP만 받는다. 확장자가 아니라 파일 앞부분 바이트로 판별한다. 파일당 10MB, 메시지당 4장. 서버는 원본만 저장하고 축소본을 만들지 않는다(각 공급사가 큰 이미지를 자체 축소한다). |
| E3 | 저장은 `<data>/rooms/<id>/attachments/<첨부ID>.<ext>`. 이름은 서버가 만든다. 메시지·API는 경로가 아닌 첨부 ID만 주고받는다. |
| E4 | 사용자 첨부: `POST /api/rooms/{id}/attachments`(multipart, 필드 `file`) → `Attachment`. 이어서 `POST /api/rooms/{id}/messages`에 `attachments: [id…]`. 다른 방의 ID나 이미 다른 메시지에 붙은 ID는 400. 메시지에 붙지 않은 업로드는 24시간 뒤 서버 시작 시 정리한다. |
| E5 | 에이전트 이미지 공유: 응답 안의 줄 `[[ATTACH:<경로>]]`. 정상 종료(`done`)한 응답에서만 처리한다. 허용 루트는 그 턴의 작업 폴더(방 workspace 또는 파트 worktree)와 서버 scratch 폴더다. `filepath.EvalSymlinks` 후 루트 안인지 확인하고, 형식·크기를 E2로 검사한 뒤 즉시 attachments로 복사한다. 실패하면 그 첨부만 거부하고 이유를 system 메시지로 남긴다(응답 자체는 유지). chat 모드는 파일 접근이 없으므로 `[[ATTACH]]`를 처리하지 않는다. |
| E6 | 에이전트가 직접 캡처하는 것은 write 모드에서만이다(셸 권한이 있는 모드). read 모드는 이미 있는 이미지 파일을 `[[ATTACH]]`로 올리는 것만 된다. 프롬프트 규칙에 이 차이를 적는다. |
| E7 | 공급사별 전달: **Claude**는 stream-json 사용자 메시지의 image 블록(base64), **Codex**는 `--image <파일>`(resume에서 동작하는지 구현 전에 실측; 안 되면 이 계약을 고치자고 보고), **agy**는 프롬프트의 파일 경로와 `--add-dir <attachments 폴더>`. 세 경우 모두 프롬프트 본문에 `[첨부 a1b2: image/png 1280×720 "파일명"]` 한 줄을 남겨 어떤 메시지의 첨부인지 알게 한다. 전달 실패는 그 턴의 오류로 드러낸다. |
| E8 | 참가자 간 요청: 응답 안의 줄 `[[REQUEST:@<좌석ID>]] <요청 내용 한 줄>`. 정상 종료한 응답에서만 만들며, discussion·review 턴은 G3에 따라 거절한다. 받는 좌석의 턴을 기존 @멘션과 같은 규칙(`max_chain`, 자동 실행, 사람 승인 없음)으로 큐에 넣되, 파트가 있으면 G2에 따라 대기한다. 요청을 전달하는 턴이 시작되면 `in_progress`. 받는 쪽이 응답 끝 신호 블록에 `[[REQUEST_DONE:<요청ID>]]` 또는 `[[REQUEST_REJECT:<요청ID>]] <이유>`를 쓰면 `done`·`rejected`가 되고, 그 응답 메시지가 결과다. 신호 없이 끝나면 `pending`으로 되돌아가 사람이 볼 수 있게 남는다(조용한 완료 처리 금지). 이미 소비한 큐 항목은 pending 요청만으로 빈 프롬프트 턴을 다시 실행하지 않는다. 사람은 요청을 취소할 수 있다(`cancelled`). |
| E9 | 요청 기록은 `<data>/rooms/<id>/requests.jsonl`(상태 변화마다 한 줄 추가, 읽을 때 마지막 상태). Snapshot에 `requests`, SSE의 기존 `{type,data}` 형식에서 `type: "request"`, `data: Request`로 요청 하나를 보낸다. 이름 붙은 `event: request`는 사용하지 않는다(`fb2d47b`). |
| G1 | `[[REQUEST_DONE:...]]`·`[[REQUEST_REJECT:...]] 이유`·`WORK:DONE`·`[[DISCUSSION:...]]`는 응답 끝의 연속된 신호 줄 블록에서 읽는다. 각 신호는 자기 줄에 쓰고 블록 안의 순서는 자유다. 여러 요청을 한 턴에 완료·거절할 수 있다. 본문·빈 줄로 블록을 끊으면 그 앞의 완료·거절 신호는 거절 사유를 남긴다. `[[ATTACH:...]]`·`[[REQUEST:@...]]`는 본문 어디서나 자기 줄이면 된다. |
| G2 | working·fixing 파트를 맡은 좌석에 온 요청은 파트 종료까지 `pending`으로 둔다. 리뷰·병합 대기 등 후속 단계에서도 방 세션을 돌려받기 전에는 시작하지 않는다. 파트 세션(최초·수정·일반 후속·리뷰)에 받은 요청과 그 원본 메시지·첨부를 넣지 않는다. 요청 때문에 생긴 큐 항목은 파트가 merged·abandoned가 된 뒤 기존 큐 규칙으로 처리한다. `wait_reason`으로 현재 파트의 대기 사유를 제공한다. |
| G3 | discussion·review 턴의 `[[REQUEST:@...]]`는 요청을 만들지 않고 거절 사유를 남긴다. `[[REQUEST`로 시작하는 줄은 콜론 유무와 관계없이 마커로 취급하며, 형식이 틀리면 명시적으로 거절한다. 잘못된 요청 줄을 일반 멘션으로 실행하거나 조용히 없애지 않는다. |

## 2. 타입

```go
type Attachment struct {
	ID     string `json:"id"`     // 서버 발급
	Name   string `json:"name"`   // 원래 파일명(표시용)
	Mime   string `json:"mime"`   // image/png | image/jpeg | image/webp
	Bytes  int64  `json:"bytes"`
	Width  int    `json:"width"`
	Height int    `json:"height"`
	By     string `json:"by"`     // "user" 또는 좌석 ID
	At     int64  `json:"at"`
}
// Message에 추가: Attachments []Attachment `json:"attachments,omitempty"`
// Message에 추가: Requests []string `json:"requests,omitempty"` // 이 메시지가 만든 요청 ID

type Request struct {
	ID        string `json:"id"`
	From      string `json:"from"`       // 좌석 ID
	To        string `json:"to"`         // 좌석 ID
	Text      string `json:"text"`
	SourceMsg string `json:"source_msg"` // 요청을 만든 메시지 ID
	Status    string `json:"status"`     // pending|in_progress|done|rejected|cancelled
	ResultMsg string `json:"result_msg,omitempty"`
	Reason    string `json:"reason,omitempty"` // rejected 사유
	WaitReason string `json:"wait_reason,omitempty"` // pending 수신 좌석의 현재 파트 대기 사유
	At        int64  `json:"at"`
}
```

## 3. API

```text
POST   /api/rooms/{id}/attachments                 multipart file → Attachment
GET    /api/rooms/{id}/attachments/{aid}           이미지 바이트(Content-Type = mime)
POST   /api/rooms/{id}/messages                    기존 본문 + "attachments": [aid…]
POST   /api/rooms/{id}/requests/{rid}/cancel       사람의 요청 취소
SSE    data = {"type":"request","data":Request}
```

## 4. UI

- 입력창: 붙여넣기·끌어놓기·📎 파일 선택. 전송 전 미리보기 칩(썸네일·이름·용량·✕). 업로드 실패는 칩에 오류로 표시하고 전송을 막는다.
- 말풍선: 첨부 썸네일 그리드(지연 로드, 높이 제한). 클릭하면 라이트박스(원본, 이름, 해상도, 다운로드).
- 요청: 말풍선 안 요청 카드(보낸 이 → 받는 이, 상태 배지, 결과 메시지로 이동). 오른쪽 패널에 "요청" 섹션(미완료 우선, 사람 취소 버튼).

## 5. 에이전트 친화 원칙

실제 일은 에이전트가 한다. 사람 화면만큼 에이전트가 막히지 않고 스스로 고칠 수 있는지를 기준으로 본다.

- `[[ATTACH]]`·`[[REQUEST]]`·`[[REQUEST_DONE]]`·`[[REQUEST_REJECT]]` 규약은 고정 안내문(standingBrief)에 예시 한 줄씩과 함께 둔다. 모드별로 쓸 수 있는 것만 적는다(chat은 ATTACH 없음, 캡처는 write만).
- 서버가 마커를 거절하면(경로 탈출, 형식·크기 초과, 없는 좌석, 모르는 요청 ID) 그 사유를 모두에게 보이는 system 메시지로 남긴다. 메시지의 `notice_for`(수신 좌석)와 `notice_delivered`(전달 완료)를 함께 저장한다. 해당 좌석의 미전달 공지는 이미 대기 중인 다음 턴의 cap 밖이어도 프롬프트에 원문 그대로 넣는다. 일반 대화·첨부의 cap은 올리지 않는다. 성공한 턴에서 전달을 확정하고, 실패·취소·재시작 때는 미전달 공지를 보존한다. 수신 좌석에게는 이후 일반 대화 경로로 중복 전달하지 않는다. 다른 좌석은 기존 대화 경계로 읽는다.
- 받은 요청은 받는 에이전트의 프롬프트에 `[요청 r7 from @좌석: 내용]` 형태로 보이고, 끝낼 때 쓸 신호를 같은 줄에 안내한다.
- 종료 신호 안내는 모두 G1의 응답 끝 신호 블록을 사용한다. 파트 대기 사유는 Snapshot과 요청 SSE에서 현재 파트 상태로 계산하며, 파트 상태가 바뀌면 대기 중인 요청 뷰도 갱신한다.
- 첨부 줄(`[첨부 …]`)에는 에이전트가 다시 열 수 있는 방법(agy·Claude는 경로, Codex는 첨부됨)을 적는다.
