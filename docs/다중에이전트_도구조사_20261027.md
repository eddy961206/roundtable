# 다중 에이전트 협업 도구 조사 (2026-10-27)

여러 LLM·코딩 에이전트를 함께 쓰는 GitHub 공개 프로젝트 30개를 조사했다. roundtable에 흡수할 만한 아이디어를 골랐고, 토큰 소모를 줄이는 방법을 가장 많이 찾았다. 이 문서는 조사 보고다. 코드는 바꾸지 않았다.

## 조사 방법과 한계

- 웹 조사는 roundtable 방 `68c1e989f9bd`(read 모드)의 GPT-6.1 Sol(high) 좌석 두 개가 나눠 맡았다.
  - 조사A: 다중 모델 토론·아이디에이션 도구, 여러 CLI 에이전트를 묶는 도구
  - 조사B: 오케스트레이터·감독·검수 루프, 토큰 절감 설계
  - 두 좌석의 사용량 합계: 입력 2,090,329(캐시 1,847,424), 출력 21,643, 약 13분
- 오케스트레이터(Claude)가 30개 저장소의 존재, 스타 수, 최근 push, 보관 여부를 GitHub API로 다시 확인했다(2026-10-27 17:3x KST). 모두 실제로 있었고 스타 수도 좌석 보고와 맞았다.
- 핵심 아이디어 다섯 개는 README 원문과 대조했다: Agent Mail 수신함·파일 예약, NTM `/compact` 뒤 감소 확인과 시차 실행, PAL `clink` 격리 문맥, Deep Agents 도구 출력 디스크 보관·요약, Overstory 메일 버스.
- 외부 도구는 실행하지 않았다. 절감률도 측정하지 않았다. 외부 문서의 수치(예: Deep Agents의 85% 압축 기준, 20,000토큰 보관 기준)는 원문 문서를 따로 열어 보지 않았으므로 미확인이다.
- 라이선스가 있는 코드는 옮기지 않았다. 설계 아이디어만 적는다.
- "현재 대응" 칸은 roundtable `cb379c0` 기준으로 코드와 README에서 확인한 것이다.

## 5. 다음 단계 제안

코드 개발은 하지 않았다. 구현할 때는 다음 순서를 권한다.

1. 비용이 작고 오늘 문제에 직접 닿는 것부터 한다: 상위 2(누적 경고), 상위 3(서버 점유 판정), 상위 7(문맥 경보), 상위 10(요약 대기).
2. 그다음 상위 1(방 사이 직접 전달)의 계약을 정한다. 원문 전달인지 머리말 전달인지, 수신 좌석 지정 방식, 기록 표시를 결정한다.
3. 상위 4·8은 품질 위험이 있다. 그래서 같은 작업을 기존 방식과 나란히 돌려 토큰과 결과 품질을 측정한 뒤 기본값을 정한다. 2026-10-20 공유 노트 실험처럼 측정에서 이득이 없으면 채택하지 않는다.
4. 상위 5·6은 계정 식별(어느 좌석이 같은 계정인지)을 먼저 정해야 한다.
