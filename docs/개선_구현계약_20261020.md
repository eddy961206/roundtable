# 개선 구현 계약 (2026-10-20)

[개선논의_20261020.md](개선논의_20261020.md)에서 합의한 구현 순서 1~8과 사용자 결정(쟁점 A는 (가)), 그리고 사용자가 추가로 요청한 UI/UX 개선을 네 파트로 나눈다. 파트끼리 파일이 겹치지 않는다. 아래 이름과 JSON 모양은 모든 파트가 그대로 쓴다. 바꿔야 하면 구현 전에 방에 알린다.

## 1. 공유 계약

| 번호 | 계약 | 소유 |
| --- | --- | --- |
| K1 | `Message.ReplyTo string json:"reply_to,omitempty"`. 에이전트 답변 메시지에 그 턴의 계기 메시지 ID(`Turn.Group`)를 저장한다. user·system 메시지와 계기가 없는 턴은 비운다. 옛 메시지는 빈 값이고 별도 복원 경로를 만들지 않는다. | P1 |
| K2 | 결정 상태에 `proposed`를 더한다(`proposed`·`active`·`superseded`·`dropped`). 방 안 좌석이 `[[DECISION]]` 마커로 만든 카드는 반대 의견과 상관없이 항상 `proposed`다. 사람 화면의 "결정 추가"(HTTP POST)는 지금처럼 `active`다. 확정은 `PATCH .../decisions/{id}`의 `status: "active"`, 거절은 `"dropped"`. 고정 안내문의 "현재 결정"에는 지금처럼 `active`만 들어간다. | P2 |
| K3 | MCP·`roundtable rt` 쓰기 도구 `rt_update_decision`(인자: `room`, `id`, 선택 `status`·`text`·`evidence`·`dissent`·`unverified`). 기존 HTTP PATCH를 감싼다. 읽기 전용 도구 목록에는 넣지 않는다. | P2 |
| K4 | 시스템 메시지는 모두 저장한다(`addSystem`도 `AppendMessage`). 저장 오류를 `_ =`로 버리지 않는다. | P1 |
| K5 | 토론: `done`이 아닌 토론 턴은 신호를 저장하지 않고 동의·패스 집계에서 뺀다. 종료 system 메시지에 "@좌석 실패로 제외"를 적는다. `done`인데 신호가 없으면 지금처럼 CONTINUE로 처리하되, 그 좌석에 `notice_for` 공지("토론 신호가 없어 CONTINUE로 처리함")를 남긴다(`notice_marker: "discussion"`). | P1 |
| K6 | 요청이 `done`·`rejected`가 되면 서버가 요청자 턴을 넣는다(reason `mention`, Group은 결과 응답 메시지 ID, Depth는 응답 턴 +1, max_chain 적용). 응답 본문이 이미 요청자를 호출했거나 응답 턴이 discussion·review면 넣지 않는다. 계약 E8의 변경이다. | P1 |
| K7 | 이력 줄 형식은 `[#<seq> @id (label)] 본문`이다. 사람 화면도 같은 `#<seq>`를 보인다. | P3·P4 |

## 2. 파트

### P1 서버 신뢰성·흐름 (작성 Astra, 리뷰 Opus)

범위: `cmd/roundtable/`, `internal/room/hub.go`, `internal/room/requests.go`, `internal/room/work.go`, `internal/room/model.go`, `internal/room/store.go`, `internal/room/lifecycle.go`와 그 테스트.

1. `net.Listen`을 `room.NewHub`보다 먼저 실행한다(두 번째 실행이 데이터를 고치기 전에 실패).
2. K1, K4, K5, K6.
3. Markdown 내보내기의 작성자를 `@id (label)`로 쓴다.
4. `markerBrief`의 결정 줄은 `decisionMarkerForm` 상수를 그대로 쓴다(문구는 P2 소유).

### P2 에이전트 진입점·결정 카드 (작성 Opus, 리뷰 Astra)

범위: `internal/room/decisions.go`, `internal/rtmcp/`, `internal/server/decisions.go`(필요할 때만), `README.md`, `skills/roundtable/SKILL.md`, `docs/에이전트MCP_블라인드토론_결정카드_계약.md`와 그 테스트.

1. K2, K3. 마커 형식 안내(`decisionMarkerForm` 또는 곁 상수)에 "제안으로 기록되고 방 사용자가 확정해야 안내문에 들어간다"를 짧게 넣는다.
2. `rt_read`: `after_seq`를 생략하면 최신부터 `max_chars` 예산까지만 담는다. 통째로 뺀 메시지는 배열에 넣지 않고 `omitted_messages`(개수)와 `first_seq`(담긴 첫 seq)로 알린다. 남는 메시지에는 `kind`·`target`·`attachments[{id,name}]`·`requests`·`decisions`·`reply_to`를 비어 있지 않을 때만 넣는다. `rt_list_rooms`는 `limit` 기본값을 두고(입력 경계) 방마다 스냅샷 전체 대신 목록에 필요한 필드만 보낸다.
3. MCP `initialize` instructions에 SKILL.md의 두 규칙(timed_out이면 재전송하지 말고 읽기, 사람이 진행 중인 방에서 토론 시작·요청 취소는 사람에게 확인)을 넣는다.
4. `rt_discuss` 설명에 "시작 전에 이미 답이 있으면 블라인드 1라운드는 호출 N회를 더 쓴다"를 넣는다.
5. README·SKILL·계약 문서를 바뀐 동작에 맞춘다.

### P3 안내문 (작성 Argon, 리뷰 Astra)

범위: `internal/room/prompt.go`와 프롬프트 테스트(`prompt_test.go`, `prompt_brief_test.go`, `mention_boundary_test.go`).

1. "@claude, @codex, @agy는 …" 고정 문장을 방의 활성 좌석 데이터로 만든다. 활성 좌석이 2명 이상인 공급자만 나열하고, 없으면 그 줄을 넣지 않는다.
2. 재개 턴의 "응답 끝 신호 블록" 한 줄은 토론 턴이나 파트 턴일 때만 넣는다(요청 블록은 자체 안내가 있다).
3. K7 이력 줄 형식.
4. 바뀐 문구가 안내문 키를 바꿔 고정 안내문이 한 번 다시 가는 것은 정상이다.

### P4 화면 UI/UX (작성 Fable, 리뷰 Argon)

범위: `web/` 전체(`index.html`, `style.css`, `js/*`). 서버 코드는 바꾸지 않는다.

1. K7: 메시지마다 작은 `#seq`를 보인다(클릭하면 그 메시지 링크 복사 또는 이동).
2. K1: `reply_to`가 있는 답변에 "↩ #N" 표시(클릭하면 그 메시지로 이동). 같은 `reply_to`를 가진 답변이 2개 이상이면 "같은 질문의 답 k/n" 표시로 병렬 답변을 묶어 알아보게 한다.
3. K2: 결정 패널에서 `proposed` 카드를 구분해 보이고 "확정"(`active`)·"거절"(`dropped`) 버튼을 둔다.
4. 블라인드 토글 옆에 "시작 전에 이미 답이 있으면 블라인드는 호출 N회를 더 씁니다" 힌트.
5. **UI/UX 점검**: 별도 포트·데이터 폴더의 시험 서버로 주요 화면(방 목록, 대화, 참가자 카드, 작업 보드, 요청·결정 패널, 새 방 대화상자, 좁은 화면)을 직접 캡처해 보고, 사용성 문제를 최대 5개 골라 고친다. 고친 것마다 전후 캡처를 `[[ATTACH:]]`로 올리고 이유를 적는다. 기능을 새로 만들지 말고 기존 화면의 정리·가독성·일관성·접근성을 다룬다.
6. 수정 후 `python tools/modcheck.py web/js` 0건.

## 3. 공통

- fallback·조용한 우회 금지, 계약 위반은 즉시 실패, 호환 계층 지양. 공개 레포이므로 내부 회사명·로컬 절대 경로를 코드·문서에 넣지 않는다.
- 커밋 메시지는 한국어(`type: [scope] 설명` + 본문).
- 검증: `go vet ./...`, `go test ./...`, `python tools/modcheck.py web/js`.
- 시험 서버는 각자 다른 포트와 임시 데이터 폴더를 쓴다. 8787과 `~/.roundtable`은 건드리지 않는다.

## 4. 구현 결과 (2026-10-20)

방 `9eea90ac7dff`(write, 자동모드)에서 네 파트가 모두 교차 리뷰를 통과했다(P1 3라운드, P2 3라운드, P3·P4 1라운드). main 반영은 `5637638`이다.

- **서버 자동 검증 정지:** P2를 통합 branch에 병합한 뒤 서버의 `go test ./...`가 900초 제한에 걸려 대기열이 멈췄다(`blocked{verify}`). 출력에는 작은 패키지만 있었고 room·rtmcp·server 결과가 없었다. 당시 go.exe는 하위 프로세스 없이 CPU를 계속 썼다. 같은 통합 상태를 오케스트레이터가 직접 돌리면 전부 통과했다(room 196초). 네 작성자가 같은 시간대에 각자 Go 빌드·테스트를 돌려 빌드 캐시 경합이 생긴 것으로 추정하지만 확인하지 못했다.
- **수동 통합:** verify retry는 파트를 수정 단계로 돌려보내므로 쓰지 않았다. 오케스트레이터가 별도 worktree에서 p2 병합 위에 p3·p4·p1을 `--no-ff`로 병합했다. `discussion_blind_test.go` 충돌 1건은 p1·p2가 같은 테스트를 K2에 맞춰 각자 고친 것이라 p2 구간을 남겼다. `go vet`, `go test -count=1 ./...`(room 179초), `modcheck` 0건을 확인하고 main에 fast-forward했다. 방의 작업 보드는 p2 `blocked`, 나머지 `queued` 상태로 남아 있다.
- **화면 확인:** 새 빌드의 별도 시험 서버에서 Haiku 5.5 두 좌석(high) 병렬 답으로 `#seq`, `↩ #1`, "같은 질문의 답 1/2", 결정 제안 카드와 확정 버튼(→`active`), 블라인드 비용 힌트를 확인했다. 마커 결정 2건은 모두 `proposed`로 들어갔다.
- **남은 것:** 작업 계획에서 여러 작성자가 동시에 무거운 빌드를 돌릴 때 서버 verify가 지연·정지하는 문제의 원인 확인. 요청 결과 자동 회신은 단위 테스트로만 확인했고 실제 CLI로 돌려보지 않았다. 후순위 후보(trace text_delta 제외, 외부 에이전트 출처 표시, 사용량 폴링 축소, 고아 프로세스 방지)는 구현하지 않았다.
