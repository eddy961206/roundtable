- **이전 버전**: `b332d3b` (agy 긴 입력 파일 전달까지 들어간 시점). 재개 턴마다 고정 안내문을 다시 보내고, 추론 수준을 바꾸면 세션을 새로 시작하고, agy 입력은 24KB 이하면 명령줄·넘으면 scratch 파일로 보낸다.
- **현재 버전**: `main` (측정 시점 `361ef51` 이후). 주요 절감 변경은 다음과 같다.
  - `f12f065` 재개 턴은 고정 안내문 대신 한 줄 알림만 보내고, 추론 수준만 바뀌면 세션을 유지한다.
  - `286b982` agy 입력을 stdin stream-json으로 보낸다.
  - 그 밖에 역할 카드·표식 안내가 늘어 첫 턴 안내문은 오히려 커졌다. 비교는 이 증가분까지 포함한 버전 전체 비교다.
- 두 버전을 별도 바이너리·별도 포트·별도 데이터 폴더로 띄우고 같은 스크립트를 동시에 돌렸다. 모델·계정·시각이 같아 서버 쪽 조건 차이는 최소화했다.
- 측정 시각: 2026-10-20 새벽(KST). 같은 시나리오를 2회 반복했다.

## 시나리오

`tools/token_ab/` 의 스크립트를 그대로 쓴다.

| 스크립트 | 내용 |
|---|---|
| `turns.py` | Opus(claude-opus-5-5)·Argon(gemini-4-argon) 두 자리, 약 3,600자 방 메모. 질문 8개를 둘 다에게 보낸다. 7번째 질문 직전에 두 자리의 추론 수준을 low → medium으로 바꾼다. |
| `long_input.py` | Argon 한 자리에 36,656바이트 메시지 1개(가운데에 비밀 코드). 이전 버전의 24KB 명령줄 한도는 넘고, 기록 클립 한도(60KB)는 넘지 않는 크기. 3회 반복. |
| `summarize.py` | 두 결과 JSON을 턴별로 비교한다. |

수치의 뜻:
- **Opus 새 입력** = `input_tokens + cache_creation_input_tokens`. 캐시에서 읽지 못하고 새로 처리한 입력이다. `total_cost_usd`는 세션 누적값이라 세션별 마지막 값을 더했다.
- **Argon 비캐시 입력** = 턴의 `context_tokens`(누적 `input_tokens`의 턴별 증가분과 같다). **Argon 캐시 입력**은 누적 `cache_read_tokens`의 턴별 증가분이다.

- 추론 수준을 바꿔도 세션이 유지되어, 새 세션의 안내문·기록 재전송(약 1만 토큰)이 사라졌다.
- 응답 시간은 두 회차 모두 줄었지만 편차가 커서 절감 근거로 쓰지 않는다.

## 결과 2 — Argon (agy): 토큰 절감은 확인되지 않음

| 항목 | 1회차 이전 → 현재 | 2회차 이전 → 현재 |
|---|---|---|
| 첫 턴 비캐시 입력 | 16,262 → 15,700 | 15,453 → 15,701 |
| 재개 턴 2~6 비캐시 입력 | 17,493\*, 4,077, 4,054, 4,047, 4,029 → 3,431, 3,476, 3,391, 3,543, 3,428 | 평균 2,080 → 2,808 (**+35%**) |
| 6번째 턴 전체 문맥(비캐시+캐시) | 25,540 → 22,759 (−11%) | 25,848 → 22,580 (−13%) |
| 추론 수준 변경 직후 턴 비캐시 입력 | 16,795 → 24,233 (**+44%**) | 17,127 → 24,057 (**+40%**) |
| 8턴 비캐시 입력 합 | 69,004 → 60,590 (−12%) | 45,363 → 56,583 (**+25%**) |
| 8턴 전체 처리 입력(비캐시+캐시) | 159,799 → 165,123 (+3%) | 160,691 → 164,443 (+2%) |

\* 이전 버전 1회차 2턴은 캐시를 전혀 읽지 못했다(`cache_read_tokens` 0). 서버 쪽 캐시 미스로 보이며, 1회차의 −12%는 이 한 턴 때문이다.

- 현재 버전은 턴마다 보내는 양이 적어 문맥이 천천히 자란다(6번째 턴 기준 −11~13%).
- 그러나 재개 턴의 비캐시 입력은 2회차에서 오히려 35% 많았다. 원인은 확인하지 못했다. 프롬프트 원문을 남기지 않아, agy가 어느 지점부터 캐시를 다시 쓰는지 비교할 수 없었다.
- 추론 수준을 바꾸면 세션은 유지되지만 agy가 캐시를 버리고 전체 문맥을 비캐시로 다시 읽는다. 이전 버전은 새 세션을 열어 안내문과 최근 기록만 보냈기 때문에 이 턴은 이전 버전이 40~44% 적다.
- 결론: agy는 8턴 기준 전체 처리량이 이전과 같은 수준(+2~3%)이다. 추론 수준 변경 턴의 증가가 재개 턴 절감을 상쇄한다.

## 결과 3 — agy 긴 입력(36,656바이트): 시간 절감, 토큰은 같음

| 항목 | 이전 (scratch 파일) | 현재 (stdin) |
|---|---|---|
| 비밀 코드 정답 | 3/3 | 3/3 |
| 입력 토큰 (3회) | 23,327 / 23,348 / 23,337 | 23,764 / 22,943 / 22,927 |
| 출력 토큰 | 100 / 115 / 100 | 11 / 11 / 11 |
| 도구 호출 | `view_file` 1회씩 | 없음 |
| 응답 시간 (3회) | 16.9 / 22.7 / 19.0초 (평균 19.5초) | 8.6 / 12.1 / 8.2초 (평균 9.6초, **−51%**) |

- 파일 전달은 모델이 `view_file`로 파일을 한 번 더 읽어야 해서 왕복이 하나 늘었다. 입력 토큰은 결국 같은 내용을 읽으므로 거의 같다.
- 처음에는 232KB 메시지로 측정했다. 두 버전 모두 기록 클립(메시지 60KB, `renderHistory`)에 걸려 가운데 코드를 받지 못했다. 이 클립은 프롬프트에 "뒷부분 생략"을 명시하는 의도된 상한이라 비교에서 뺐다. 60KB를 넘는 자료는 메시지 대신 첨부나 작업 폴더 파일로 넘겨야 한다.

## 측정 한계

- 회차가 2회뿐이다. Opus 결과는 두 회차 방향과 크기가 일치하지만, Argon은 회차 사이 편차(이전 버전 재개 턴 2,080 대 4,050)가 효과 크기보다 크다.
- Codex·OpenCode는 이번 측정에 넣지 않았다. 재개 턴 안내문 제거는 공급사 공통 변경이라 비슷한 방향을 예상하지만 실측은 아니다.
- 비용은 CLI가 보고한 `total_cost_usd`이며 구독 한도 소모량과 같다고 확인하지 않았다.
- agy 한도가 캐시 입력을 얼마로 세는지 확인하지 않았다. 그래서 Argon은 비캐시와 전체 처리량을 함께 적었다.

## 다시 재는 법

1. 비교할 두 커밋을 각각 빌드한다(이전 커밋은 `git worktree add --detach`로 받는다).
2. 두 바이너리를 다른 포트와 다른 `-data` 폴더로 띄운다.
3. 두 서버에 `python tools/token_ab/turns.py <주소> <이름> <결과.json> short`를 동시에 실행한다.
4. `python tools/token_ab/summarize.py <이전.json> <현재.json>`으로 비교한다.
5. 긴 입력은 `python tools/token_ab/long_input.py <주소> <이름> <결과.json> 3`으로 잰다.
