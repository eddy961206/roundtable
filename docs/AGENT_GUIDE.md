# 에이전트 안내서: Roundtable을 오케스트레이터로 쓰기

이 문서는 사람이 AI 에이전트(예: Claude Code)를 대리인 겸 오케스트레이터로 삼아 Roundtable을 쓸 때, 그 에이전트가 읽는 문서다. 기능을 찾고, 비싼 실수를 피하고, 실패를 스스로 고치는 데 필요한 것만 담는다. 사람용 화면 설명은 [README](../README.md)에 있다.

- 짧은 진입점: [skills/roundtable/SKILL.md](../skills/roundtable/SKILL.md)(셸 스킬), MCP `initialize`의 `instructions`(MCP 연결).
- 이 문서의 사실은 2026-10-27~28 코드(`internal/room`, `internal/rtmcp`, `internal/agent`)와 실제 다중 모델 운영 기록에서 확인했다. 관측값에는 관측 시각과 조건을 적었다.

## 1. 먼저 알아야 할 다섯 가지

1. **방의 모든 좌석은 자기 차례마다 토큰을 쓴다.** 방 하나에 작업 하나만 넣는다. 끝난 방에는 더 보내지 않는다.
2. **오케스트레이터는 말을 옮기지 않는다.** 작성 좌석과 검수 좌석이 같은 방에서 `[[REQUEST:@좌석]]`로 직접 주고받게 하고, 오케스트레이터는 판정 줄과 head만 읽는다(`rt wait --summary true`). 다른 방의 답을 넘겨야 하면 읽고 다시 쓰지 말고 `rt forward`로 원문을 옮긴다.
3. **기다릴 때는 폴링하지 않는다.** `rt post`(대기 없이)로 받은 `seq`를 `rt wait --rooms <방>:<seq>`에 준다.
4. **`timed_out`은 취소가 아니다.** 같은 메시지를 다시 보내지 말고 `resume_after_seq`로 이어 읽는다.
5. **서버는 `install` 다음 `restart`로만 바꾼다.** 다른 세션이 같은 서버를 쓴다. 프로세스를 직접 죽이지 않는다.

## 2. 연결

| 방식 | 언제 | 방법 |
|---|---|---|
| 셸 `roundtable rt` | 셸이 있는 에이전트. 평소 문맥 비용이 없다. | `roundtable rt help`, `roundtable rt <명령> --help` |
| MCP `roundtable mcp` | 셸이 없거나 도구 호출이 편한 에이전트. 도구 설명이 매 턴 문맥에 들어간다. | `claude mcp add --transport stdio roundtable -- roundtable mcp --url <서버>` |
| HTTP API | `rt`에 없는 기능(아래 3.2). | `http://127.0.0.1:<포트>/api/...`, loopback만 허용 |

- 서버 주소 기본값은 `http://127.0.0.1:8787`이다. Windows에서 8787이 예약 범위에 걸리면 다른 포트(예: 18787)로 띄운다. 그때는 `roundtable rt --url http://127.0.0.1:18787 ...`처럼 명령 이름 앞에 `--url`을 둔다.
- `rt` 명령 이름은 MCP 도구 이름에서 `rt_`를 뺀 것이다. 인자·검증·결과가 같다.
- 출력은 한 줄 JSON이다. 종료 코드 1은 검증·실행 실패, 2는 명령 형식 오류다. stderr의 사유를 읽고 고친다. 같은 명령을 그대로 반복하지 않는다.
- 긴 본문은 `--text -`로 stdin에 넣는다. 셸 인용에서 백틱·`$`가 사라지는 사고를 막는다.

## 3. 기능 색인

### 3.1 `rt` 명령(= MCP `rt_*` 도구)

| 명령 | 언제 쓰나 |
|---|---|
| `list_rooms [--limit N] [--include_archived true]` | 방 id·좌석 id·`enabled`를 찾을 때. 좌석은 이름이 아니라 id로 부른다. 보관한 방은 실행 중이 아니면 빠진다. |
| `seats [--rooms <방>,...] [--limit N]` | 여러 방의 좌석 상태를 한 번에 볼 때. 좌석마다 `status`(idle·queued·running), `ctx`(마지막 호출 문맥)·`window`, `session`(이어 쓰는 세션 유무), `turns`, `last_seq`·`last`(최근 40개 메시지 안의 마지막 답: 상태와 판정·신호 줄, 판정 줄이 없으면 끝 3줄)가 나온다. `--rooms`를 빼면 보관하지 않은 최근 방 `limit`개(기본 20). 다음 일을 배정하기 전 인계할 좌석을 고를 때 쓴다. |
| `create_room --title --workspace --mode --participants '<JSON>' [--turn_timeout_minutes N] [--quiet_done true] [--max_chain N]` | 작업 하나에 방 하나를 만들 때. `participants[]`는 `provider`·`model`·`effort`·`label`·`role`·`fork_from`. 결과의 좌석 id를 적어 둔다. 긴 작성 턴이 예상되면 턴 시간 상한(5~720분, 기본 45)을 늘린다. 작성·검수 방이면 `--quiet_done true`와 왕복에 맞는 `--max_chain`(1~20, 기본 4)을 준다(6.2). |
| `post --room --text [--target <좌석>] [--wait_seconds N]` | 지시를 보낼 때. 여러 방이면 `--wait_seconds` 없이 보내고 `seq`를 모은다. |
| `read --room [--after_seq N] [--max_chars N]` | 답 원문을 읽을 때. `after_seq`보다 큰 seq만 나온다. 생략하면 최신부터 20000자다. |
| `wait --rooms <방>:<seq>,... [--timeout_seconds N] [--summary true]` | 여러 방 중 먼저 끝난 방을 기다릴 때. 서버 SSE로 깨어나 폴링이 없다. `--summary true`면 좌석 답마다 판정 줄(`판정`·`결론`·`verdict` 뒤 `:`)과 마커·신호 줄만 받고 `chars`로 원래 길이를 본다. 판정 줄이 없는 답(진행 보고 등)은 끝 산문 3줄이 판정 대신 남는다. |
| `forward --room <받는 방> --from_room <방> --seq N [--target <좌석>] [--note "한 줄"]` | 다른 방의 답(검수 결과 등)을 원문 그대로 넘길 때. 받는 좌석 이력에 출처(방·#seq·작성자)가 붙고, 원문 속 @멘션·마커는 실행되지 않는다. 받은 좌석이 원문을 답에 인용할 때는 ``` 코드 블록 안에 둔다. 코드 블록 밖에 다시 적은 `[[REQUEST]]`·`[[ATTACH]]`·`[[DECISION]]` 줄은 그 좌석 자신의 마커로 실행된다. |
| `usage --rooms <방>,...` | 좌석·방별 토큰(`input`=`cached`+`uncached`, `output`, `max_context_tokens`, `turns`, `errors`)을 볼 때. `messages.jsonl`을 직접 파싱하지 않는다. |
| `update_room --room [--title] [--note] [--workspace] [--mode] [--seat_input_budget N] [--room_input_budget N] [--input_warn_tokens N] [--context_warn_percent N] [--turn_timeout_minutes N] [--compact_window_tokens N] [--quiet_done true\|false] [--archived true\|false] [--max_chain N]` | 방 메모(협업 규칙)를 바꾸거나, 지워진 worktree 대신 새 작업 폴더를 줄 때. 좌석·방 누적 입력 상한(0=없음), 누적 입력 경고 간격(0=1천만, -1=끔), 문맥 경보 비율(0=70, -1=끔), Claude 좌석 자동 압축 기준 `compact_window_tokens`(0=CLI 기본, 100000~1000000)도 여기서 정한다. 압축 기준은 긴 세션의 입력을 줄이지만 턴이 길어진다(A/B -38% 입력, +57% 시간). |
| `discuss --room --rounds N [--blind_first false]` | 여러 모델 의견을 라운드로 겨루게 할 때. 이미 같은 질문에 답했으면 `--blind_first false`. |
| `requests --room` / `cancel_request --room --request` | 좌석 간 `[[REQUEST]]`의 상태를 보거나, 잘못 나간 요청을 취소할 때. |
| `handoff --room --seat [--note "한 줄"] [--fresh true]` | 한 좌석의 세션이 길어졌을 때(문맥 경보, 작업이 바뀌는 지점). 좌석이 지금 세션에서 인계 요약(근거 위치·결정·남은 일·다음 할 일)을 쓰고, 다음 턴부터 그 요약과 이후 메시지만 든 새 세션을 쓴다. 기반에서 포크한 좌석은 기반을 다시 포크한다(`--fresh true`면 기반 없이). 결과의 `seq`로 `wait`. 조용한 좌석만 받는다: 실행·대기 중인 턴, 미완료 파트, 토론, 한도·예산 보류, 이미 인계됨, 세션 없음, 기반 방 삭제(`--fresh true` 필요)면 사유와 함께 거절한다. 요약 턴은 끼어들기·요청·마커를 처리하지 않고, 인계 뒤 첫 턴이 전달될 때까지 매 턴 새 세션이 요약부터 시작한다. 2026-10-28 A/B에서 다음 검수·수정 턴 입력이 43% 줄었고 결함 발견·수정 결과는 같았다(`docs/토큰효율_측정_20261028.md`). |
| `cancel_turn --room --seat` | 좌석의 실행 중인 턴 하나만 멈출 때(중복 턴 등). 좌석은 켜진 채로 남아 요청을 계속 받는다. |
| `apply_markers --room --seq N` | 오류로 끝난 답(`pending_markers` 있음)이 끝까지 쓰였음을 확인한 뒤 그 답의 마커를 한 번 실행할 때. |
| `decisions --room` / `update_decision --room --id --status active\|dropped` | 좌석이 남긴 결정 카드(`proposed`)를 확인하고 확정·거절할 때. AGREE는 검증이 아니다. |
| `archive_rooms --rooms <방>,... [--archived false]` | 끝난 방을 목록에서 숨길 때(보관). 기록·세션은 남고 계속 쓸 수 있다. 실행·대기 중인 방은 `failed`에 사유가 남는다. `--archived false`는 보관 해제. 되돌릴 수 없는 삭제 대신 이것을 쓴다(6.5). |
| `version` | 실행 중인 빌드가 공개 main보다 뒤처졌는지 볼 때. |

**읽기·기다리기 세부**
- `post --wait_seconds N`의 결과가 `timed_out:true`면 실행은 계속 중이다. 다시 보내지 않고 결과의 `resume_after_seq`로 `read --after_seq <resume_after_seq>`를 실행한다. 보낸 seq를 그대로 쓰지 않는다. `live:true`(실행 중인 답에 끼워 넣은 입력)면 그 답의 seq가 보낸 seq보다 작아서 빠진다.
- `read`를 `--after_seq` 없이 부르면 최신 메시지부터 `max_chars`까지만 담는다. 빠진 오래된 메시지는 `omitted_messages`(개수)와 `first_seq`(담긴 첫 seq)로 알린다. 답의 `reply_to`는 그 답이 응답한 메시지의 seq다.
- `wait`는 한 방이라도 끝나면(실행·대기 턴이 없고 seq 뒤에 좌석 답이 있음) 돌아온다. `ready[]`에 끝난 방의 새 메시지, `waiting`에 남은 방이 있다. 끝났다는 것은 성공했다는 뜻이 아니다. 답의 상태(`done`·`error`)를 본다. `after_seq`를 빼면 대기 시작 뒤의 답만 세므로 이미 도착한 답을 놓친다.
- `list_rooms`를 주기적으로 부르는 대기 스크립트는 쓰지 않는다.

### 3.2 HTTP로만 되는 것

아래는 `rt`·MCP에 없다. 한글이 든 본문은 UTF-8 파일로 저장해 `curl --data-binary @파일`로 보낸다(7절 "UTF-8이 아닌 요청").

| 기능 | 요청 | 비고 |
|---|---|---|
| 기존 방에 좌석 추가 | `POST /api/rooms/{방}/participants` `{"provider","model","effort","label","role","count","fork_from"}` | 결과는 방 전체 JSON이다. 새 좌석 id는 `participants[]` 끝에 있다. 새 좌석의 첫 턴은 방 기록 전체를 받는다(4절). |
| 좌석 켜기·끄기, 이름·모델·추론 수준·역할 | `PATCH /api/rooms/{방}` `{"participants":[{"id":"<좌석>","enabled":true}]}` | 모델·추론 수준은 실행 중에 바꿀 수 없다. 모델을 바꾸면 다음 턴은 새 세션이다. |
| 토론 라운드·블라인드 기본값 | `PATCH /api/rooms/{방}` `{"discussion_rounds":2,"blind_first_default":false}` | |
| 좌석 하나 중지 | `POST /api/rooms/{방}/participants/{좌석}/stop` | **좌석을 끈다(`enabled=false`).** 7절 참고. |
| 턴 하나만 취소 | `rt cancel_turn --room --seat` 또는 `DELETE /api/rooms/{방}/turns/{턴}` | 좌석은 켜진 채로 둔다. 실행 중인 답 메시지의 `turn_id`가 턴 id다. |
| 방 전체 중지 | `POST /api/rooms/{방}/stop` | 실행 중인 턴과 대기열을 모두 비운다. |
| 좌석 제거 | `DELETE /api/rooms/{방}/participants/{좌석}` | 기록·사용량은 남고 다시 부를 수 없다. |
| 방 세션 초기화 | `POST /api/rooms/{방}/reset` | 모든 좌석이 다음 턴에 새 세션으로 시작한다. |
| 방 삭제 | `DELETE /api/rooms/{방}` | 기록까지 지운다. 되돌릴 수 없다. 사람에게 확인받는다. 목록을 줄이려면 `rt archive_rooms`(보관)를 쓴다. |
| 공급사·모델 목록 | `GET /api/providers[?refresh=true]` | 5절 능력표의 근거. |
| 방 원문·대기열 | `GET /api/rooms/{방}?limit=N` | 메시지·좌석·요청·대기열 스냅샷. |

### 3.3 `tools/orchestrate` 도우미

roundtable 방과 Gitea PR을 오케스트레이터 한 명이 이어 붙일 때 쓴다. 설정·관측 한계는 [tools/orchestrate/README.md](../tools/orchestrate/README.md)에 있다. 어떤 스크립트도 병합하지 않는다.

| 도구 | 언제 쓰나 |
|---|---|
| `rtwait.sh <방>:<seq> ...` | `rt wait`를 백그라운드로 돌리고 끝난 방의 마지막 답 끝부분만 볼 때. |
| `gpost.sh comment\|pr` + `glint.py` | Gitea에 댓글·PR을 파일 본문으로 게시할 때. 게시 전에 초안 문구·로컬 경로·빈 코드 조각을 막는다. |
| `assign_fix.sh <PR> <리뷰id> <작성방> <branch>` | 상대 개발자의 리뷰를 작성 방에 수정 지시로 넘길 때. 작성 좌석 하나에게만 보낸다(이름에 `writer`·`작성`, 아니면 `TARGET=<좌석 id>`). 작성 좌석 문맥이 크면 먼저 `rt handoff`(6.4). |
| `queue_review.sh <label> <worktree> <작성방> <검수방> "<초점>"` | 작성이 끝난 worktree를 재기반하고 검수 방에 검수를 요청할 때. 검수 좌석 하나에게만 보낸다(이름에 `reviewer`·`검수`, 아니면 `TARGET=<좌석 id>`). |
| `ci_wait.sh <PR>` | PR head의 CI 결과를 기다릴 때(병합하지 않음). |
| `reviewer_check.py` / `reviewer_watch.sh <since>` | 상대 개발자의 새 댓글·리뷰를 확인하거나 기다릴 때. |
| `pr_overlap.py [--integrate]` | 병합 전에 열린 PR끼리 줄 충돌·같은 파일·같은 절·스키마 번호 충돌을 볼 때. |
| `after_merge.py <PR> [--assign]` | 병합 직후 영향받는 열린 PR을 찾고 재기반 지시를 보낼 때. |
| `worktree_claims.py check\|claim\|release\|list` | 한 worktree에 두 방이 동시에 일하지 않게 막을 때. |

## 4. 좌석이 메시지를 받는 규칙

코드: `internal/room/hub.go`의 `PostUser`, `deltaForContext`, `chainMentions`, `internal/room/requests.go`의 `finishMarkers`.

**누가 부름을 받나**
- 사람·오케스트레이터 메시지에 `--target`이 있으면 그 좌석만 부른다. 없고 멘션도 없으면 **켜진 좌석 전원**을 부른다. `@좌석ID`·`@이름`·`@공급사`(예: `@codex`)·`@all`은 해당 좌석만 부른다. 코드 블록·인라인 코드 안의 `@`는 멘션이 아니다. ``` 코드 블록 안의 `[[...]]` 마커 줄도 실행하지 않는다.
- 좌석의 답에 있는 일반 `@멘션`도 그 좌석을 부른다. 답 본문에 다른 좌석 이름을 `@`로 쓰지 말라고 메모에 적어 두면 의도하지 않은 호출을 막는다.

**차례가 오면 무엇을 받나**
- 좌석은 **마지막으로 본 뒤의 메시지**를 묶어 받는다. 차례를 부른 메시지 seq까지만 받는다.
- **다른 좌석을 `target`으로 지정한 메시지는 받지 않는다.** 자기 답도 다시 받지 않는다. 실행 중인 다른 좌석의 미완성 답은 건너뛰었다가 다음 차례에 받는다.
- **첫 턴(세션이 없을 때)은 방 기록 전체를 받는다.** 기존 방에 좌석을 추가하면 그 좌석의 첫 턴 입력이 방 기록만큼 커진다. 긴 방에 검수 좌석을 붙이지 말고 새 방을 만든다. 예외로 `handoff`한 좌석의 새 세션은 인계 요약 seq부터 받는다(그 앞 기록은 요약으로 대신한다). 포크 좌석은 기반 세션을 복사해 시작하지만, 첫 턴에 받는 방 기록 규칙은 같다.
- 재개 턴은 방 안내문(참가자·메모·규칙)을 다시 보내지 않는다. 메모(`note`)를 바꾸면 안내문이 달라져 다음 턴에 다시 보낸다.

**연쇄 호출과 `max_chain`**
- 좌석 답의 `@멘션`과 `[[REQUEST:@좌석]]`은 그 좌석의 새 턴을 만든다. 요청 결과(`[[REQUEST_DONE]]`·`[[REQUEST_REJECT]]`)는 요청한 좌석을 다시 부른다.
- 사람 메시지로 시작한 턴의 깊이는 0이고, 연쇄마다 1씩 는다. 깊이가 `max_chain`(기본 4)을 넘으면 서버가 "연쇄 한도에 도달해 멈췄어" 시스템 메시지를 남기고 멈춘다. 작성 → 검수 → 수정 → 재검수 왕복은 한 번에 깊이 2를 쓴다. 왕복 셋을 허용하려면 6 이상이 필요하다. 2026-10-27 운영에서는 8을 썼다.
- `discuss`·작업 분배 리뷰 턴에서는 연쇄 호출과 새 `[[REQUEST]]`를 만들지 않는다.

**마커**
- `[[REQUEST:@좌석ID 또는 @이름]] 내용`은 한 줄이어야 한다. 대상은 다른 **켜진** 좌석이어야 한다. 꺼진 좌석이면 "비활성 또는 삭제된 좌석", 이름이 없으면 "일치하는 활성 좌석 없음"으로 거절되고, 사유는 그 좌석의 다음 프롬프트로 돌아간다.
- 요청 결과 신호(`[[REQUEST_DONE]]`·`[[REQUEST_REJECT]]`)는 답 맨 끝의 신호 줄 묶음에 둔다. 그 묶음 안에는 다음 요청 `[[REQUEST:@좌석]]`·`[[ATTACH]]`·`[[DECISION]]` 줄이 섞여도 된다(예: 완료 신호 다음 줄에 재검수 요청). 빈 줄이나 일반 글이 끼면 그 앞의 결과 신호는 거절된다. f14f132 이전 서버는 결과 신호 뒤에 요청 줄이 오면 결과 신호를 거절했다.
- **마커는 `done`으로 끝난 답에서만 자동 실행된다.** 오류로 끝난 답의 `[[REQUEST]]`·`[[REQUEST_DONE]]`·`[[DECISION]]`·`[[ATTACH]]`는 실행되지 않고, 답에 `pending_markers`(남은 마커 수)와 시스템 안내가 남는다. 답을 읽어 끝까지 쓰였으면 `apply_markers --room --seq N`(화면의 **마커 실행**)으로 한 번 실행한다(7절 agy 유휴 시간 초과).

**실행 중인 좌석에 보내기**
- `--target`으로 실행 중인 좌석에 보내면 Claude 좌석은 실행 중인 턴에 끼워 넣는다(`live:true`). Codex·agy·OpenCode 좌석은 그 좌석의 우선 대기 턴이 된다.
- 출력을 낸 뒤 오류로 끝난 턴은 그 턴이 받은 메시지를 "전달됨"으로 기록한다. 같은 메시지를 기다리던 대기 턴은 CLI를 부르지 않고 건너뛴다. 출력 전에 실패한 턴과 사용자가 중단한 턴의 메시지는 다음 턴에 다시 전달된다. 이 동작이 없던 서버(2026-10-27 `a458c08` 이전)에서는 답을 다 쓴 뒤 오류로 끝난 턴 뒤의 대기 턴이 같은 일을 한 번 더 했다.

- **실행 검수 좌석은 write 모드로 둔다.** 변형 시험·main과의 비교·임시 빌드가 필요한 검수는 read 모드로는 못 한다. 지시에 "저장소 파일은 바꾸지 말 것. 임시 파일은 작업 폴더 밖 임시 폴더에 만들 것"을 건다. write 모드의 셸은 쓰기를 기술적으로 막지 않으므로(OpenCode 파일 도구의 작업 폴더 제한만 예외) 이 지시가 사실상 유일한 제한이다.
- OpenCode 검수 좌석은 검수 대상 worktree를 작업 폴더로 준다. 작업 폴더 밖 파일은 read·write 모두 파일 도구로 읽지 못한다.
- 같은 공급사·모델도 여러 좌석을 둘 수 있다. 한도는 계정 단위라 좌석 수만큼 늘지 않는다.
- Codex 좌석의 첫 안내문에는 시험·빌드 같은 긴 명령을 `yield_time_ms` 30000으로 시작하고 빈 `write_stdin`은 300000으로 기다리라는 규칙이 자동으로 들어간다. 1초 간격 확인 호출(무거운 세션 입력의 18~45%)을 줄이려는 것이라 지시에 따로 적지 않는다. 2026-10-28 실방에서 45초 명령이 모델 호출 약 3번으로 끝났다.
- agy 좌석의 첫 안내문에는 백그라운드로 넘어간 긴 명령에 `manage_task` 상태 확인·`schedule` 타이머를 걸지 말고 한 줄만 쓰고 기다리라는 규칙이 자동으로 들어간다. 명령이 끝나면 agy가 알림으로 다시 깨운다. 10분 시험 A/B에서 규칙 없는 좌석이 상태를 75번 확인하며 입력 495만 토큰을 쓴 경우가 있었고, 규칙 있는 좌석은 0번·2.8만 토큰이었다(시간·결과 같음). 화면에 "재검수 중…" 같은 줄이 반복되면 이 확인 고리다.
- 문맥 경보 비율의 분모는 CLI가 보고한 모델 문맥 창이다(Claude는 결과의 `modelUsage[모델].contextWindow`, 예: Opus·Sonnet 5.5는 1,000,000). 1e52df5 이전 서버는 Claude를 200,000으로 계산해 경보가 4~5배 높게 보였다.

## 6. 오케스트레이터 플레이북

### 6.1 역할 나누기

오케스트레이터(가장 비싼 모델)가 할 일:
- 작업을 나누고 방마다 시작 지시를 보낸다.
- 방들 사이의 판단(우선순위, 충돌, 재기반 순서)을 한다.
- push·PR·병합·외부 게시를 한다. 병합은 사람이 정한 조건(예: 상대 개발자 승인)을 확인한 뒤에만 한다.
- 상대 개발자(사람 리뷰어)에게 대응한다.

오케스트레이터가 하지 않을 일:
- 작성 좌석과 검수 좌석 사이에서 검수 원문을 옮기는 일. 옮기면 같은 긴 본문을 오케스트레이터가 읽고(입력) 다시 쓰는(출력) 데 가장 비싼 토큰을 두 번 쓴다. 좌석끼리 `[[REQUEST]]`로 직접 주고받게 한다.
- 방의 답 전체를 매번 읽는 일. 판정 줄과 head(커밋 해시)만 읽는다. `rtwait.sh`는 마지막 답 끝부분만 보여 준다.

### 6.2 작업(PR) 하나 = 방 하나

1. 작업마다 worktree를 만든다.
2. 방 하나에 **작성 좌석**과 **다른 공급사의 검수 좌석**을 함께 둔다. 같은 공급사끼리는 같은 맹점을 공유한다.
3. 방 메모(`note`)에 협업 규칙을 적는다(아래 예시).
4. `max_chain`을 왕복 수에 맞게 늘린다(왕복 셋이면 6 이상, 여유를 두면 8).
5. 작성 좌석에게만 `--target`으로 시작 지시를 보낸다. `--target` 없이 보내면 검수 좌석도 동시에 일을 시작한다.
6. `rt wait`로 기다리고, 판정 줄과 head만 읽는다.
7. 작업이 끝나면 방에 더 보내지 않는다. 다른 작업을 같은 방에 넣지 않는다.

방 하나에 여러 작업을 넣으면 안 되는 이유: 좌석은 차례마다 마지막으로 본 뒤의 메시지를 모두 받는다. 다른 작업의 긴 답이 다음 차례 입력으로 쌓이고, CLI 세션도 계속 커진다. 2026-10-27 운영에서 여러 단계 작업을 이어 맡은 agy 좌석 하나(gemini-4-argon, 14턴)의 누적 입력이 약 9,700만 토큰, 한 호출 최대 문맥이 약 25.6만 토큰이었다(17:42 KST `rt usage` 관측).

방 메모 예시(작성 좌석 `w1`, 검수 좌석 `r1`):

```text
협업 규칙
- 작성(@w1)은 구현과 시험이 끝나면 답 끝에 한 줄로 [[REQUEST:@r1]] <worktree> head <해시> 검수 요청 을 쓴다.
- 검수(@r1)는 첫 줄에 "판정: 통과" 또는 "판정: 수정 필요"를 쓴다.
- 수정이 필요하면 지적 표(번호·심각도·파일:줄·재현·확신도)만 담아 [[REQUEST:@w1]] 수정 요청 을 쓴다. 설명을 반복하지 않는다.
- 통과면 요청을 만들지 않는다. 오케스트레이터가 판정 줄과 head를 읽는다.
- 세 번째 왕복이면 멈추고 "판정: 사람 판단 필요"와 남은 이견만 쓴다.
- 답 본문에 다른 좌석을 @로 부르지 않는다. 부를 때는 [[REQUEST]]만 쓴다.
- 검수자는 저장소 파일을 바꾸지 않는다. 임시 파일은 작업 폴더 밖 임시 폴더에 만든다.
```

만드는 명령 예시:

```bash
roundtable rt --url http://127.0.0.1:8787 create_room --title "작업 X" --workspace <작업 X worktree> --mode write --quiet_done true --max_chain 8 \
  --participants '[{"provider":"codex","label":"w1","effort":"high"},{"provider":"agy","model":"gemini-4-argon","label":"r1"}]'
roundtable rt update_room --room <방> --note - < note.txt
roundtable rt post --room <방> --target <w1 좌석 id> --text - < task.md
```

요청을 받은 좌석은 답 끝에 `[[REQUEST_DONE:요청ID]]`를 붙이라는 안내를 받는다. 기본으로 이 결과 신호는 요청한 좌석을 다시 부른다. 그러면 검수가 통과여도 작성 좌석이 "승인됐어"만 쓰는 턴을 한 번 더 돌며 문맥 전체를 다시 읽는다(10-27~28 운영 실측: 그런 턴 하나가 캐시 읽기 59만~67만 토큰). 그래서 작성·검수 방은 `--quiet_done true`로 만든다.
- `quiet_done`인 방에서는 완료 신호(`REQUEST_DONE`)가 요청자를 부르지 않는다. 거절 신호(`REQUEST_REJECT`)는 그대로 부른다.
- 요청을 받은 좌석의 프롬프트에 "이어서 할 일이 있으면 `[[REQUEST:@요청자]]`로 따로 요청하라"는 안내가 붙는다. 위 메모 규칙(수정이 필요하면 `[[REQUEST:@w1]]`)과 같으므로 수정 왕복은 그대로 돈다.
- 작성 좌석은 다음에 부를 때 검수 답을 이력으로 함께 받는다. 잃는 정보는 없다.
- 2026-10-28 A/B(작은 문서 과제 2쌍): 검수 통과 뒤 작성 좌석 턴(입력 4.2만~4.4만, 그 좌석의 문맥 크기)이 없어졌고 검수 판정·커밋은 같았다. 수정 경로도 그대로 돌았다(`docs/토큰효율_측정_20261028.md` T5).
- 이미 만든 방은 `rt update_room --room <방> --quiet_done true`로 켠다.

`create_room` 결과의 좌석 id가 `label`과 다를 수 있다. `[[REQUEST:@이름]]`은 공백 없는 고유한 이름이면 동작하지만, 메모에는 좌석 id를 적는 것이 가장 확실하다.

### 6.3 기반 세션 포크와 함께 쓰기

작업마다 새 방을 만들면 좌석마다 같은 공통 문서(규칙·설계 기록·계약)를 처음부터 다시 읽는다. 공통 문서는 **기반 방**의 좌석에 한 번만 읽히고, 작업 방의 좌석은 그 세션을 복사(포크)해서 시작한다. 포크마다 문맥이 따로라 같은 기반에서 여러 좌석을 포크해도 서로의 작업을 보지 않는다. 계약은 [기반문맥_포크_계약.md](기반문맥_포크_계약.md), 실측은 [기반문맥_포크_측정_20261027.md](기반문맥_포크_측정_20261027.md)에 있다.

1. 기반 방을 만든다. 결과의 `room`과 `participants[0].id`를 적어 둔다.
   `roundtable rt create_room --title "<프로젝트> 기반" --workspace <저장소> --mode read --participants '[{"provider":"codex","model":"<모델>","effort":"high","label":"기반"}]'`
2. 공통 문서를 읽힌다. 작업은 시키지 않는다.
   `roundtable rt post --room <기반방> --text "공통 문서 A, B, C를 끝까지 읽어. 작업은 하지 말고 '준비됨'만 답해." --wait_seconds 600`
3. 작업 방을 만들 때 좌석에 `fork_from`을 준다. 공급사·모델은 기반 좌석과 같아야 한다(생략하면 기반 좌석 값). 작업 폴더·모드·추론 수준은 달라도 된다.
   `--participants '[{"provider":"codex","label":"w1","fork_from":{"room":"<기반방>","seat":"<기반좌석>"}}, ...]'`
4. 작업 지시에는 공통 문서를 다시 읽으라는 말을 넣지 않는다.

- 6.2의 방 하나에 작성 좌석(기반 A에서 포크)과 검수 좌석(다른 공급사의 기반 B에서 포크)을 함께 둔다. 기반 방은 공급사·모델마다 하나씩 필요하다.
- 작업마다 git worktree가 다르면 기반 방은 저장소 본체에, 작업 방은 각자의 worktree에 둔다. 폴더가 다르면 포크 첫 턴에 "기반의 작업 폴더는 A, 지금은 B"가 자동으로 붙는다. 상위 폴더를 작업 폴더로 두는 우회는 쓰지 않는다(좌석이 다른 작업의 worktree까지 읽고 쓸 수 있다).
- 기반 방에는 작업을 보내지 않는다. 기반이 커지면 모든 포크가 그 짐을 이어받는다. 공통 문서가 바뀌면 기반 방을 새로 만든다.
- 기반 좌석이 실행 중이면 포크 첫 턴은 실패한다.
- 실측(문서 74KB, 작은 읽기 작업 3개): Codex는 작업당 비캐시 입력이 약 29%, Claude는 작업당 비용이 약 82% 줄었다. 기반 1회 비용은 작업 2~3개면 회수됐다.

**포크가 없는 agy 좌석을 이어 쓸 때**
- agy는 포크하지 못한다. agy 좌석은 새 좌석으로 두고 필요한 문서만 지시에 적거나, 같은 좌석을 이어 쓴다.
- 이어 쓰면 두 번째 검수부터 비캐시 입력이 약 40% 줄었다. 그러나 문맥이 검수마다 커지고 한 검수 안의 모든 호출이 그 문맥 전체를 다시 보낸다(gemini-4-argon, 작은 검수 6건: 캐시 입력 합계가 새 좌석의 6배).
- 다음 검수가 이전 검수 내용을 실제로 써야 할 때(같은 변경의 재검수, 지적 반영 확인)만 이어 쓴다. 관련 없는 검수는 새 방을 만든다.
- `rt usage`의 좌석 문맥이 새 좌석이 필요한 문서를 다시 읽는 양의 2배를 넘으면(실측 추이에서 잡은 어림값) 같은 일을 이어 갈 때는 `rt handoff`로 그 좌석을 인계 요약에서 새 세션으로 시작하게 하고, 관련 없는 다음 일이면 새 방을 만든다. `handoff`는 agy 좌석에도 된다(포크가 아니라 새 세션이라서).
- 이어 쓰는 좌석의 추론 수준은 바꾸지 않는다. 바꾸면 그 턴은 문맥 전체를 비캐시로 다시 읽는다.
- 문맥이 매우 커지면 CLI가 스스로 압축한다. 압축 뒤에는 이전 검수의 세부를 잃었을 수 있다.

### 6.4 여러 방을 동시에 굴릴 때

- 한 worktree에는 한 번에 한 방만 일하게 한다(`worktree_claims.py`).
- `--wait_seconds` 없이 각 방에 보내고, `rt wait --rooms A:<seq>,B:<seq>`로 먼저 끝난 방부터 처리한다. 결과의 `waiting` 값을 다음 대기에 그대로 쓴다.
- 대기 시간이 셸 도구 제한보다 길면 백그라운드로 실행하고 끝났다는 알림을 받는다.
- 병합 전후로 `pr_overlap.py`·`after_merge.py`를 돌려 열린 PR끼리의 충돌을 미리 본다.
- 상대 개발자의 리뷰를 같은 작성 방에 다시 맡기기 전에 `rt seats --rooms <방>,...`로 좌석 `ctx`를 본다(여러 방을 한 번에 읽는다. 방마다 `GET /api/rooms/{방}`을 부르는 스크립트는 쓰지 않는다). 수십만 토큰이면 먼저 `rt handoff --room <방> --seat <작성 좌석> --note "곧 받을 일"`을 보내고 그 `seq`로 기다린 뒤 배정한다. 이어 쓰면 수정 턴의 모델 호출마다 그 문맥 전체를 다시 읽는다(2026-10-28 VMS-next 리뷰 대응 4건 배정 전 Opus 작성 좌석 3개가 42만~46만 토큰이었다).

### 6.5 끝난 방 정리

- 작업이 끝난 방은 `rt archive_rooms --rooms <방>,<방>,...`으로 보관한다. `list_rooms`·`seats`·화면 목록에서 빠지고, 기록·세션·사용량은 남는다. 보관한 방도 메시지를 보내면 그대로 돈다(실행 중에는 목록에 다시 보인다).
- 보관한 방까지 보려면 `list_rooms --include_archived true`. 되돌리려면 `archive_rooms --rooms <방> --archived false`.
- 화면에서는 방 우클릭 메뉴의 "보관", 또는 검색창에 공통 이름(예: 실험 제목)을 넣고 "검색된 방 N개 보관"을 누른다.
- 삭제(`DELETE /api/rooms/{방}`)는 되돌릴 수 없으니 사람이 확인한 방만 지운다.

## 7. 실패 유형과 대처

| 증상 | 원인 | 대처 |
|---|---|---|
| 좌석 답이 한도 오류(429, rate/usage/free limit, quota)로 끝나고 "한도 오류로 …까지 이 좌석의 새 턴을 보류함" 안내 | 공급사 한도 도달. 서버가 그 좌석만 재시도 시각(오류에 없으면 10분 추정)까지 보류한다. `list_rooms` 좌석의 `held_until`(ms)·`held_reason`에 보인다. | 기다리면 시각이 지난 뒤 대기 턴이 저절로 돈다. 바로 다시 해 보려면 그 좌석을 `--target`으로 지정해 보낸다(보류가 풀림). 무료 한도면 다른 모델 좌석으로 바꾼다. |
| "턴 보류: 좌석(방) 누적 입력 …이 예산 상한 …에 도달" 안내 | 방의 `seat_input_budget`·`room_input_budget`에 닿았다. 그 좌석(방이면 전 좌석)의 새 턴을 시작하지 않는다. 메시지는 남아 있다. | 의도한 상한이면 새 좌석·포크로 바꾸거나 일을 줄인다. 계속하려면 `update_room --seat_input_budget <더 큰 값 또는 0>`. 다음 턴에 남은 메시지가 함께 간다. |
| 답이 `error`이고 `error_kind: turn_timeout`, "턴 시간 상한 N분을 넘어 중단됨" | 턴이 방의 시간 상한(기본 45분)을 넘었다. 사용자가 누른 취소(`cancelled` "중단됨")와 다르다. 출력이 있었으면 받은 메시지는 전달된 것으로 기록된다. | 답 원문을 읽고 어디까지 했는지 확인한다. 이어서 할 일만 다시 보낸다. 긴 작업이면 `update_room --turn_timeout_minutes 120`처럼 늘린 뒤 보낸다(5~720분). |
| "이 방 누적 입력이 …을 넘음"·"문맥이 모델 한도의 n%에 도달" 안내 | 한 세션을 오래 이어 써서 턴마다 입력이 커졌다. | 작업이 바뀌는 지점이면 `rt handoff --room --seat`로 인계 요약을 남기고 새 세션으로 바꾼다. 경고만 하며 턴은 막지 않는다. 이 안내는 사람·오케스트레이터용이라 좌석 프롬프트에는 들어가지 않는다(`user_only`). |
| `rt post`·`rt forward`가 409 "작업 폴더 사용 중: 방 …이 같은 작업 폴더 …에서 실행 중" | 같은 폴더를 쓰는 다른 방(둘 중 하나라도 write)이 실행 중이다. 작성 중인 worktree를 다른 방이 동시에 검수·수정하지 못하게 막는다. | 그 방의 턴이 끝난 뒤(`rt wait`) 다시 보낸다. 이미 대기열에 들어간 턴은 그 방이 끝나면 저절로 시작한다. git 작업 트리 안의 폴더만 잠근다. `.git`이 없는 worktree 모음 폴더(`_worktrees` 등)를 쓰는 방끼리는 함께 실행되니 `tools/orchestrate/worktree_claims.py`로 등록한다. |
| agy 답 본문은 끝까지 있는데 턴이 `error`(스트림 유휴 시간 초과)이고, 답 안의 `[[REQUEST]]`가 실행되지 않음 | 서버는 오류로 끝난 답의 마커를 스스로 실행하지 않는다(답이 잘렸을 수 있음). | 답을 읽고 끝까지 쓰였으면 `apply_markers --room --seq N`으로 실행한다. 잘렸으면 그 좌석에 다시 시도를 보낸다. |
| 턴이 "작업 폴더가 없어 실행하지 않았어"로 실패 | 방의 worktree가 PR 병합 정리 등으로 지워졌다. | `rt update_room --room <방> --workspace <새 폴더>`. 방과 좌석 세션은 유지된다. 실행 중에는 바꿀 수 없다. |
| HTTP 요청이 400 "UTF-8" 오류로 거절 | Windows `curl -d '{...}'`에 한글을 넣으면 콘솔 코드 페이지 바이트로 넘어간다. 서버는 UTF-8이 아닌 본문을 거절한다. | 본문을 UTF-8 파일로 저장하고 `curl --data-binary @파일`로 보낸다. `rt` 명령은 이 문제가 없다. |
| 이어 쓰는 좌석의 턴이 연속으로 실패하거나, `rt usage`의 `max_context_tokens`가 모델 문맥 한도 근처 | 세션 문맥이 한도까지 커졌다. | 같은 지시로 재시도하지 않는다. 턴이 아직 성공하면 `rt handoff`로 새 세션으로 바꾼다. 요약 턴마저 실패하면 새 좌석(또는 새 방)으로 바꾸고, 필요한 상태만 지시에 요약해 준다. |
| `[[REQUEST:@좌석]]`이 "비활성 또는 삭제된 좌석"·"일치하는 활성 좌석 없음"으로 거절 | 좌석 중지 API를 썼다. `POST .../participants/{좌석}/stop`은 턴만 멈추지 않고 그 좌석을 `enabled=false`로 끈다. | `PATCH /api/rooms/{방}` `{"participants":[{"id":"<좌석>","enabled":true}]}`로 다시 켠다. 그리고 멈춘 일을 새 메시지로 다시 보낸다(취소된 요청은 자동으로 다시 돌지 않는다). 턴만 멈추려면 `rt cancel_turn --room --seat`(또는 `DELETE /api/rooms/{방}/turns/{턴}`)을 쓴다. |
| 사람 메시지가 "활성 대상 없음"으로 거절 | `--target` 좌석이 꺼져 있다. | 위와 같이 좌석을 켠다. |
| "연쇄 한도(N)에 도달해 멈췄어" 시스템 메시지 | 작성·검수 왕복이 `max_chain`을 넘었다. | 의도한 왕복이면 `rt update_room --room <방> --max_chain 8` 뒤 멈춘 좌석에게 직접 보낸다. 의도하지 않았으면 메모의 왕복 규칙을 확인한다. |
| 포크 첫 턴이 "기반 좌석 …가 실행 중이라" 실패 | 기반 턴이 끝나지 않았다. | 기반 턴이 끝난 뒤 다시 보낸다. |
| `rt wait`·`rtwait.sh`가 SSE 끊김 오류로 끝남 | 서버가 재기동됐다. | 답이 없는 것으로 보지 않는다. 같은 `방:seq`로 다시 기다린다. |
| 서버 교체 스크립트가 다른 세션의 실행 중인 턴을 끊음 | 상태 조회 실패를 "유휴"로 해석하고 프로세스를 직접 내린 사고가 있었다. | `<새 빌드> install <서버 exe>` 다음 `<서버 exe> restart --url <서버> --timeout 30m`만 쓴다. 서버가 유휴 확인과 종료를 한 잠금 안에서 한다. 시간 안에 유휴가 되지 않으면 이전 서버를 그대로 둔다. |

## 8. 서버를 새 빌드로 바꿀 때

사람이 교체를 허락한 경우에만 한다. 절차는 [README의 새 빌드로 교체하기](../README.md#새-빌드로-교체하기)와 [CONTRIBUTING.md](../CONTRIBUTING.md#실행-중인-서버-교체)를 따른다.

1. `<새 빌드>.exe install <서버 exe 경로> [<다른 사본 경로>...]`
2. `<서버 exe 경로> restart --url http://127.0.0.1:<포트> --timeout 30m` — 원래 서버를 띄우던 방식(백그라운드 셸 등)으로 실행한다. 이 프로세스가 새 서버가 된다.
