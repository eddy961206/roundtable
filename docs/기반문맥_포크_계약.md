# 기반 문맥 포크 계약 (v1)

같은 프로젝트의 작업을 여러 방에 나눠 맡길 때, 공통 문서를 좌석마다 다시 읽는 비용을 없애는 기능이다. 공통 문서는 **기반 방**의 좌석이 한 번 읽고, 작업 방의 좌석은 그 CLI 세션을 **복사(포크)**해서 첫 턴을 시작한다. 실측과 비교는 [기반문맥_포크_측정_20261027.md](기반문맥_포크_측정_20261027.md)에 있다.

## 1. 문제

- 작업마다 새 방(= 새 CLI 세션)을 만들면, 좌석마다 같은 공통 문서(AGENTS.md, 설계 기록, 계약 문서 등)를 처음부터 다시 읽는다. 문서를 읽는 도구 호출마다 그때까지의 문맥 전체를 다시 보내므로, 읽기 단계만으로 수만~수십만 토큰과 몇 분이 든다.
- 방 하나를 계속 재사용하면 이전 작업의 짐이 문맥에 쌓여 호출마다 보내는 양이 커지고, 작성 문맥과 검수 문맥을 분리해야 하는 규칙(같은 세션이 쓰고 검수하지 않는다)도 깨진다.

## 2. 비교한 안

| 안 | 공통 문서 재읽기 | 작업 간 짐 | 작성·검수 분리 | 판단 |
| --- | --- | --- | --- | --- |
| A. 작업마다 새 방(현재) | 매번 | 없음 | 됨 | 기준 |
| B. 기반 세션 + 포크 | 없음(기반에서 1회) | 없음(포크마다 기반에서 출발) | 됨(포크마다 별도 세션) | **채택** |
| C. 장기 역할 좌석 + 작업 경계 압축 | 없음 | 요약으로 줄지만 남음 | 역할별 좌석으로만 됨 | 비채택. 헤드리스 CLI에서 압축을 지시할 공식 방법이 공급사마다 없거나 다르고, 요약 품질이 작업 결과를 좌우한다. |
| D. 프로젝트 문맥 팩(첫 턴에 파일 내용 주입) | 도구 호출은 없지만 첫 턴마다 같은 양을 보냄 | 없음 | 됨 | 비채택. B보다 매번 보내는 양이 크고, 무엇을 넣을지 roundtable이 정해야 한다. |

## 3. 결정

| 번호 | 결정 |
| --- | --- |
| F1 | 좌석 생성 입력 `participant_specs[].fork_from = {"room": "<기반 방 ID>", "seat": "<기반 좌석 ID>"}`. 방 생성(`POST /api/rooms`)과 참가자 추가(`POST /api/rooms/{id}/participants`), `rt_create_room`(`roundtable rt create_room`)에서 같다. |
| F2 | 생성 시 검증(실패하면 방·좌석을 만들지 않는다): 기반 방·좌석이 있고 제거되지 않았다. 기반 좌석에 세션이 있다. 공급사가 같다. 공급사가 포크를 지원한다(Claude·Codex·OpenCode, agy는 거절). 모델이 같다(생략하면 기반 좌석의 모델·추론 수준을 쓴다). 작업 폴더·모드·추론 수준은 달라도 된다(v2, F10). |
| F3 | 좌석에는 `Participant.fork = {room, seat, session}`(생성 시점의 기반 세션 ID)을 저장한다. 실제 복사는 그 좌석의 첫 턴에 CLI가 한다. 첫 턴이 끝나 새 세션 ID가 생기면 이후 턴은 그 세션을 평소처럼 재개하고, `fork`는 출처 기록으로 남는다. |
| F4 | 첫 턴 시점에 기반 방이 없거나 기반 좌석이 실행 중이면 그 턴을 오류로 끝낸다(반쯤 쓰인 기반을 복사하지 않는다). |
| F5 | 첫 턴 프롬프트는 일반 첫 턴과 같다(전체 고정 안내문 + 이 방의 대화 전체). 여기에 "다른 방의 기반 세션을 복사해 시작했다. 읽은 내용은 다시 읽지 말고 쓰되, 그 방의 이름·참가자·역할·규칙·요청은 무효다. 바뀌었을 수 있는 파일은 필요할 때 다시 확인한다"는 한 단락을 더한다. |
| F6 | 공급사 명령: Claude `--resume <기반> --fork-session`, Codex `codex exec fork … <기반> -`, OpenCode `--session <기반> --fork`. |
| F7 | 사용량: Codex 포크의 `turn.completed` 누적값에는 기반 thread의 사용량이 들어 있지만 포크 rollout에는 기반의 token_count가 없다. 그래서 기반 rollout의 마지막 누적값을 턴 시작 전 값으로 쓴다(기반 rollout을 못 찾으면 실행하지 않고 실패). Claude 포크의 `total_cost_usd`는 기반 세션 누적 비용을 포함하므로, 기반 방에 기록된 기반 세션의 마지막 `session_cost_usd`를 뺀다. |
| F8 | 세션 초기화, 모델 변경, 방 모드·작업 폴더 변경은 `fork`도 지운다. 그 뒤 첫 턴은 기반 없이 새 세션으로 시작한다. |
| F9 | 미루는 것: 웹 화면의 포크 입력(지금은 HTTP API·`rt`·MCP만), 작업 계획 파트 세션의 포크. |
| F10 | v2(2026-10-27): 다른 작업 폴더로도 포크한다. Claude Code 2.1.299, Codex 0.162.1, OpenCode 2.1.4에서 폴더 A의 세션을 폴더 B에서 포크하면 기억을 유지하고 도구는 B에서 실행됨을 확인했다(v1의 "Claude는 같은 폴더에서만 세션을 찾는다"는 가정은 틀렸다). `fork.dir`에 기반 방의 CLI 실행 폴더(채팅 모드는 빈 값)를 저장하고, 폴더가 다르면 첫 턴 맨 앞에 "기반 세션의 작업 폴더는 A였고 지금은 B다. 읽은 경로는 B 기준으로 다시 해석하고 바뀌었을 수 있는 파일은 다시 확인하라"는 한 줄을 넣는다. 작업마다 다른 git worktree를 쓸 때는 기반 방을 저장소 본체나 아무 worktree에 두고, 작업 방은 각자의 worktree를 작업 폴더로 준다. |

## 4. JSON

```jsonc
// POST /api/rooms (발췌)
{ "title": "작업 X 작성", "workspace": "<저장소>", "mode": "write",
  "participant_specs": [ { "provider": "codex", "label": "작성",
                           "fork_from": { "room": "<기반 방 ID>", "seat": "<기반 좌석 ID>" } } ] }

// room.json participants[] (발췌)
{ "id": "codex-…", "provider": "codex", "model": "gpt-6.1-sol", "effort": "high",
  "session_id": "",                                   // 첫 턴 뒤 포크 세션 ID
  "fork": { "room": "<기반 방 ID>", "seat": "<기반 좌석 ID>", "session": "<기반 세션 ID>", "dir": "<기반 방 작업 폴더, 채팅 모드는 빈 값>" } }

// rt_create_room 결과
{ "room": "<방 ID>", "participants": [ { "id": "codex-…", "label": "작성", "provider": "codex", "model": "gpt-6.1-sol", "enabled": true } ] }
```

## 5. 쓰는 법

1. 기반 방을 읽기 모드로 만들고, 공통 문서를 읽힌다. 작업은 시키지 않고 "준비됨"만 답하게 한다.
2. 작업마다 새 방을 만들고 좌석에 `fork_from`을 준다. 작업 지시에는 공통 문서를 다시 읽으라는 말을 넣지 않는다.
3. 검수 좌석도 같은 기반에서 다른 방으로 포크한다. 작성 방의 대화는 검수 좌석에 보이지 않는다.
4. 기반 방에는 작업을 보내지 않는다. 공통 문서가 바뀌면 기반 방을 새로 만든다.

명령 예시는 [skills/roundtable/SKILL.md](../skills/roundtable/SKILL.md)에 있다.
