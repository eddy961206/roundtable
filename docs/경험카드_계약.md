# 경험 카드 계약 (v0 초안)

2026-10-20 초안. 같은 날 설계 방(Opus 5.5·GPT-6 Astra·Gemini 4 Argon, 모두 high, 읽기 모드)에서 검토했다. **세 좌석 모두 이 초안의 구현(P1~P3)을 보류하고 11절의 0단계부터 하자고 합의했다.** 사용자는 0단계 진행을 결정했고, 결과는 11절에 있다. 3~8절은 보류된 v0 설계로 남겨 두고, 알려진 결함은 10절에 적었다.

## 0. 배경

Harness²(google-research/harness2, arXiv:2610.14224)는 모델을 바꾸지 않고 모델을 둘러싼 지시문·도구·메모리를 고쳐 성능을 올린다. 그중 "실행 근거가 뒷받침하는 교훈만 누적해 다음 과제에 쓴다"는 부분(EXPERIENCE.md)을 roundtable에 가볍게 옮긴 것이 경험 카드다. 편집안 여러 개를 실제로 돌려 비교하는 탐색(Probe)은 이 문서 범위가 아니다(2단계 안내문 A/B).

roundtable에서 대응하는 것:

| Harness² | roundtable |
| --- | --- |
| 하네스(시스템 프롬프트·가드레일·스킬 등) | 고정 안내문(`standingBrief`), 파트·리뷰 지시문, 역할 카드 |
| 실행 근거 | 방 데이터의 마커 거절 알림, 리뷰 표 형식 오류 |
| 근거 있는 교훈 누적 | 경험 카드(`experience.json`) |
| 개선 하네스가 다음 과제에 반영 | 활성 카드를 해당 모델 좌석의 안내문에 주입 |

## 1. 원칙

- **경험 카드는 모델 행동을 고치는 데만 쓴다.** 샌드박스·권한·CLI 실패 같은 실행 환경 오류는 카드로 우회하지 않고 서버에서 고친다.
- **근거 없는 카드는 없다.** 카드마다 방 데이터의 실제 메시지를 최소 1개 가리킨다. 근거가 없거나 형식이 틀린 파일은 즉시 오류로 보인다.
- **시스템은 후보를 찾고 기록한다. 활성화는 사람이 한다.** 서버는 교훈 문장을 만들지 않는다. 에이전트는 초안(proposed)까지만 만든다.
- **모델 특성을 코드에 고정하지 않는다.** 카드는 사용자가 편집하는 데이터 파일이고, 모델 glob으로 대상을 고른다(역할 카드 계약 R3와 같은 방식).
- **가볍게 유지한다.** 새 저장소·새 의존성·서버 내 LLM 호출을 만들지 않는다. 주입량에 상한을 두고, 상한을 넘은 카드는 화면에 "주입 안 됨"으로 보인다(조용히 빠지지 않는다).

## 2. 현재 데이터 (관측, 2026-10-20)

기본 데이터 폴더(`~/.roundtable`)의 방 23개를 집계했다(scratch 스크립트, 저장소에 넣지 않음).

- 완료된 에이전트 턴: 99개 (gpt-6.1-sol 29, claude-opus-5-5 22, gemini-4-argon 19, gpt-6-astra 14, claude-fable-5-1 13, gemini-3.8-flash 2).
- 마커 거절 알림: 4건. 모두 claude-fable-5-1의 `[[ATTACH:…png]]`이고, 한 파트에서 파일을 작업 폴더에서 찾지 못한 경우다. 모델 행동 문제인지 경로 처리 문제인지는 확인하지 않았다.
- 리뷰 표 형식 재요청: 0건.

후보는 당분간 드물다. 그래서 이 기능은 데이터 파일과 계산 API만으로 끝내고, 화면도 기존 모델 기록 대화상자 안에 둔다.

## 3. 결정 (초안)

| 번호 | 결정 |
| --- | --- |
| X1 | 카드는 서버 데이터 폴더의 `experience.json`에 둔다. 없으면 `{"cards": []}`로 만든다. 서버는 요청마다 다시 읽고(역할 카드 R3와 같음), 쓰기는 잠금 안에서 읽고-고치고-원자적으로 저장한다. 사용자가 파일을 직접 고쳐도 된다. |
| X2 | 증거 출처는 두 가지다. ① 마커 거절: `kind=system`이고 `notice_for`가 있는 메시지(`requests.go`의 `markerError`). ② 리뷰 표 형식 오류: `kind=agent`이고 `error`가 `리뷰 표 형식 오류`로 시작하는 메시지(`work.go`의 형식 재요청). 턴 실패(`status=error`)는 환경 오류로 보고 제외한다. 마커 거절의 마커 이름은 서버가 정한 알림 형식 `@<좌석> 마커 거절 (<마커 원문>): <사유>`에서 `[[` 뒤부터 첫 `:` 또는 `]]` 앞까지다(예: `[[ATTACH:a.png]]` → `ATTACH`). 이 형식을 바꾸면 후보 계산도 같이 고친다. |
| X3 | 후보 계산 `GET /api/experience/candidates?days=30`: 방 데이터에서 (모델, 감시 종류, 마커 이름)별로 묶어 건수·같은 기간 턴 수·최근 증거 5개·이미 연결된 카드 ID를 돌려준다. 저장하지 않고 요청 때 계산한다(역할 카드 R4와 같음). |
| X4 | 카드 상태는 `proposed`(초안) → `active`(주입) → `retired`(중단)다. `retired`는 `retired_reason`이 필수다. 삭제 대신 중단해서 효과 기록을 남긴다. |
| X5 | 활성 카드는 해당 좌석의 모델이 `match`에 맞고 카드의 `contexts`에 이번 프롬프트 종류가 있을 때 주입한다. `chat`은 `standingBrief`의 "당신의 역할" 다음, `part`는 `BuildPartPrompt`, `review`는 리뷰 단계 지시문에 들어간다. |
| X6 | 주입 상한은 프롬프트당 3개, 카드 문장은 200자 이하 한 문장이다. 정렬은 증거 수 내림차순, 같으면 `activated_at` 최신순이다. 재개 턴의 한 줄 알림에는 넣지 않는다. 카드가 바뀌면 안내문 키가 바뀌어 다음 턴에 고정 안내문이 한 번 다시 간다. |
| X7 | 효과 기록: 감시 종류가 `none`이 아닌 활성·중단 카드마다 활성화 전 30일과 활성화 후의 (건수, 턴 수)를 보인다. 표본 수를 같이 보이고 자동 중단은 하지 않는다. |
| X8 | 에이전트 진입점: MCP와 `roundtable rt`에 `rt_experience_candidates`(조회)와 `rt_experience_propose`(초안 생성)만 연다. 활성화·중단은 화면과 사람용 API(`PATCH`)로만 한다. |
| X9 | 증거에는 원문 발췌(300자 이하)를 같이 저장한다. 방이 삭제돼도 카드는 유효하고, 화면은 그 증거를 "원본 삭제됨"으로 보인다. 카드를 만들 때(`POST`)는 원본 메시지가 실제로 있어야 한다. |

## 4. JSON

```jsonc
// <데이터 폴더>/experience.json
{
  "cards": [
    {
      "id": "fable-attach-path",                 // 고유, 영문 소문자·숫자·하이픈
      "match": "claude-fable-*",                  // 모델 ID glob (path.Match)
      "contexts": ["part"],                       // chat | part | review 중 1개 이상
      "lesson": "화면 캡처는 작업 폴더 안에 저장하고 [[ATTACH:]]에는 그 폴더 기준 상대 경로를 쓴다.",
      "watch": { "kind": "marker_reject", "marker": "ATTACH" },  // kind: marker_reject | review_format | none. marker는 marker_reject일 때만 필수
      "evidence": [
        { "room": "f4d4a4b6101d", "msg": "<메시지 ID>", "excerpt": "@p1 마커 거절 ([[ATTACH:p1-onboarding.png]]): GetFileAttributesEx …" }
      ],
      "status": "active",                         // proposed | active | retired
      "author": "user",                           // user 또는 초안을 만든 좌석 "@id(model)"
      "created_at": 1792417324586,
      "activated_at": 1792417400000,              // status가 proposed면 0
      "retired_reason": ""                        // status가 retired면 필수
    }
  ]
}
```

위 카드는 형식 예시다. 실제 원인을 확인하기 전에는 이 카드를 만들지 않는다.

```jsonc
// GET /api/experience
{
  "cards": [ { /* 위 카드 필드 */,
    "injection": { "injected": true, "reason": "" },   // 상한 초과면 false와 "상한 3개 초과"
    "effect": { "before": { "count": 4, "turns": 13 }, "after": { "count": 0, "turns": 6 } }  // watch.kind가 none이면 effect 없음
  } ],
  "path": "<서버가 읽은 파일 경로>"
}

// GET /api/experience/candidates?days=30
{
  "rows": [ {
    "model": "claude-fable-5-1", "watch": { "kind": "marker_reject", "marker": "ATTACH" },
    "count": 4, "turns": 13, "card": "",           // 연결된 카드가 있으면 그 ID
    "evidence": [ { "room": "…", "msg": "…", "excerpt": "…", "ts": 1792417324586 } ]
  } ],
  "generated_at": 1792417324586
}

// POST /api/experience/cards            → 항상 status "proposed"로 만든다
// PATCH /api/experience/cards/{id}      → lesson·contexts·match 수정, status 변경(retired는 retired_reason 필수)
```

## 5. 안내문 문구 (chat 맥락)

```
이 모델에서 관측된 주의점(경험 카드):
- 화면 캡처는 작업 폴더 안에 저장하고 [[ATTACH:]]에는 그 폴더 기준 상대 경로를 쓴다.
```

주의점이 없으면 이 절을 넣지 않는다. 역할 문장처럼 "다른 관점의 지적을 막지 않는다"는 설명은 붙이지 않는다.

## 6. 화면

모델 기록 대화상자에 "경험 카드" 탭을 더한다.

- 후보 목록: 모델, 감시 종류, 건수/턴 수, 최근 증거 발췌, "초안 만들기" 버튼(문장은 사람이 쓴다).
- 카드 목록: 상태 전환(활성화·중단, 중단 사유 입력), 주입 여부와 사유, 효과(전후 건수/턴 수), 증거 원본으로 이동.
- `experience.json` 형식 오류는 탭 맨 위에 오류 원문으로 보인다.

## 7. 토큰·무게

- 추가 입력: 프롬프트당 최대 3줄 × 200자. 고정 안내문은 세션에서 한 번만 가므로 재개 턴에는 추가 비용이 없다.
- 새 의존성 없음. 후보 계산은 방 데이터를 한 번 훑는다(모델 기록 API와 같은 비용 수준).

## 8. 미루는 것

- 안내문 편집안을 실제로 돌려 비교하는 A/B 탐색(2단계).
- 서버가 LLM으로 교훈 문장을 자동 작성하는 것.
- 추론 노력·CLI 버전 단위의 카드 대상 지정(메시지에 CLI 버전이 없다).
- 다른 모델에서 얻은 교훈을 비슷한 모델로 옮기는 것.
- 효과가 없을 때 자동 중단.

## 9. 열린 질문과 설계 방 결론

설계 방 `42c3564a86d2`에서 독립 답변 1회와 반박 1회를 거쳤다. 결론 열은 세 좌석의 최종 입장이고, 사용자 결정은 아니다.

| 번호 | 질문 | 초안의 기본안 | 설계 방 결론 |
| --- | --- | --- | --- |
| Q1 | 로컬 API에 인증이 없어 에이전트도 `PATCH`로 활성화할 수 있다. MCP·`rt`에서만 막으면 충분한가? | 충분하다. | 경로를 열지 않는 것은 유지한다. 다만 보안 장치가 아니라 운영 약속이라고 명시한다. `server.go`는 루프백과 같은 출처만 검사하고 호출자를 구분하지 않는다. 결정 카드 수정·파트 승인도 같은 신뢰 모델이다. |
| Q2 | 대상을 모델 glob으로 고를지, 좌석 단위로 고를지? | 모델 glob. | 모델 glob을 유지한다. 좌석 ID는 방마다 새로 생겨 교훈이 이어지지 않는다. 기본값은 관측된 정확한 모델 ID로 하고, 계열 전체로 넓히는 것은 사람이 따로 판단한다(Astra). |
| Q3 | 주입 상한 3개가 적절한가? | 3개로 시작해 조정. | 3개·200자를 유지한다. 동률은 카드 ID로 고정한다. 안내문 키와 본문은 같은 카드 스냅샷으로 만든다(`hub.go`에서 키 계산과 본문 생성이 따로 호출됨). "효과 보고 조정"은 표본이 작아 근거가 안 된다. |
| Q4 | 리뷰 맥락 주입이 리뷰어의 독립 판단을 흐리지 않는가? | 행동 교정 카드만 `review`에 둔다. | v1에서 `review` 맥락을 뺀다. `watch.kind` 검사로는 자유문장이 판단을 유도하는지 막지 못한다. `ReviewInput`에 모델 ID가 없고 리뷰 지시문은 미리 만들어 저장된다. 리뷰 형식 재요청은 0건이고 기존 1회 자동 재요청이 있다. |
| Q5 | 마커 거절에 구조화된 필드를 더할 것인가? | 더하지 않는다. | **기본안을 뒤집는다.** `markerError`에서 당시 `Provider`·`Model`·`Effort`·`Role`, 마커 종류(거절한 분기가 이미 앎), 원인 응답 메시지 ID를 기록한다. 과거 기록은 문자열 해석으로 복원하지 않고 "구조화 이전 N건, 집계 제외"로 개수만 보인다. 문자열 해석은 당시 모델을 알 수 없고 콜론이 빠진 줄 같은 경우에 깨진다. |
| Q6 | 교훈 문장 초안은 누가 쓰는가? | 누구나. 다른 공급사 권장. | 누구나 쓰고 활성화는 사람이 한다. 다른 공급사는 권장일 뿐이다. `rtmcp`에는 호출자 좌석 정보가 없으므로 `author`는 진입점 기준 `user`·`mcp`만 둔다(Opus). 증거 발췌는 서버가 원본에서 만든다(Astra). |

## 10. 알려진 결함 (v1을 열 때 고칠 것)

1. **X2 자기모순(높음).** 리뷰 표 형식 오류도 `status=error`로 저장된다(`hub.go`의 형식 오류 처리). "턴 실패 제외"를 그대로 구현하면 출처 ②가 항상 0건이다.
2. **마커 거절의 모델 귀속 불가(높음).** 알림에는 좌석 ID만 있고 좌석 모델은 나중에 바뀔 수 있다. Q5 결론으로 해결한다.
3. **part 카드 반영 시점(높음).** `BuildPartPrompt`는 파트 세션의 첫 턴에만 쓰인다. 진행 중인 파트에는 카드 변경이 반영되지 않는다.
4. **단일 `injection.injected`는 정의할 수 없다(높음).** 상한은 (모델, 맥락)별로 잘린다. 모델·맥락별 "주입 대상"과 "상한 제외"로 보인다. 전후 수치는 효과가 아니라 "관측 건수"라고 부른다.
5. **활성 카드 수정(높음).** 승인한 내용과 주입 내용이 달라진다. 활성 카드는 중단 후 새 초안으로 대체한다. 서버 잠금은 외부 편집기를 막지 못한다.
6. **안내문 위치·문구(중간).** 역할 없는 좌석의 위치가 정의되지 않았다. 제목에 내부 용어 "경험 카드"를 쓰지 말고 `규칙:` 절 가까이에 직접 지시형으로 둔다(Argon).
7. **과잉 설계(중간).** 후보 4건에 비해 API·효과 비교·MCP 도구 2개·화면 탭이 많다. MCP 도구는 스키마 토큰을 상시 쓴다.

## 11. 0단계 (설계 방 합의, 사용자 결정 전)

카드 체계를 만들기 전에 근거부터 정확히 쌓는다.

1. **ATTACH 거절 4건의 원인을 조사한다.** 파트 턴의 작업 폴더는 파트 worktree다. 캡처를 다른 폴더에 저장했는지(모델 행동), 경로 처리 문제인지(서버) 확인한다. 서버 문제면 원칙 1에 따라 서버에서 고친다.
2. **마커 거절 기록을 구조화한다.** Q5 결론의 필드를 `markerError`에서 채운다. 과거 기록 해석 경로는 만들지 않는다.
3. **기존 모델 기록에 관측값만 더한다.** `stats.go`·`web/js/stats.js`의 표에 모델별 마커 거절 건수, 리뷰 형식 오류 건수, 구조화 이전 제외 건수 열을 더한다. 오류율이나 모델 특성으로 표현하지 않는다.

새 API, `experience.json`, 프롬프트 주입, MCP 도구는 만들지 않는다. **카드 계약 v1은 사람이 원인을 모델 행동 문제로 확인한 후보가 처음 생겼을 때 연다.** 건수 기준은 두지 않는다.

### 0단계 결과 (2026-10-20)

**ATTACH 4건의 원인은 서버 안내문이었다.** 모델 습관이 아니므로 카드 후보가 아니다.

- 관측: 파트 턴의 실행 기록에서 좌석은 캡처를 worktree의 `.cache/shots/`에 저장했다. 그다음 서버 scratch 폴더로 복사하고 `[[ATTACH:p1-onboarding.png]]`처럼 파일 이름만 썼다. 같은 이름의 파일은 scratch에 실제로 남아 있다.
- 코드: `attachmentSource`는 상대 경로를 작업 폴더(파트 worktree) 기준으로만 찾는다. scratch는 절대 경로일 때만 허용 범위로 검사한다.
- 안내문: "작업 폴더 또는 서버 scratch 안의" 파일이라고만 쓰고 예시는 파일 이름뿐이었다. 그래서 파일 이름만 쓰면 scratch에서도 찾는다고 읽을 수 있었다.
- 고친 동작: 안내문을 "상대 경로는 작업 폴더 기준이고, 서버 scratch의 파일은 절대 경로로 쓰세요"로 바꿨다. 쓰기 모드 예시는 "작업 폴더에 저장 후"로 바꿨다. 서버가 scratch에서 파일 이름을 추가로 찾는 대체 탐색은 넣지 않았다.

**구조화 기록과 표시를 구현했다.**

- `Message.notice_marker`(`attach`·`request`·`request_result`·`decision`)와 `Message.notice_msg`(거절된 줄이 있던 응답 ID)를 더했다. 당시 모델은 Q5 결론처럼 알림에 복사하지 않고 `notice_msg`가 가리키는 응답의 `model`·`effort`·`role`을 쓴다. 응답에 이미 그 턴의 값이 저장돼 있어 같은 값을 두 곳에 두지 않기 위해서다.
- 리뷰 표 형식 오류 응답에 `Message.error_kind = "review_format"`을 더했다. 문구 접두사로 판정하지 않는다.
- `GET /api/stats/models`의 행에 `marker_rejects`(종류별 건수)와 `review_format_errors`를 더했다. 응답 최상위의 `unattributed_marker_rejects`는 `notice_msg`가 없는 이전 알림의 수다. `notice_msg`가 가리키는 응답이 없으면 오류로 실패한다.
- 모델 기록 표에 "마커 거절"(칸에 마우스를 올리면 종류별 건수)과 "리뷰 형식 오류" 열을 더했다. 이전 알림이 있으면 상태 줄에 "모델 기록 이전의 마커 거절 N건은 당시 모델을 알 수 없어 표에서 뺐습니다"라고 보인다.
- 확인: `go vet ./...`, `go test ./...`, `python tools/modcheck.py web/js` 통과. 실제 방 데이터 복사본으로 띄운 새 빌드에서 이전 알림 4건이 `unattributed_marker_rejects`로 집계되고, 화면에 새 열과 안내 문구가 나오는 것을 봤다.
- 바뀐 안내문은 각 세션의 고정 안내문 키를 바꾸므로 다음 턴에 한 번 다시 전송된다.

**실제 CLI 확인과 추가 수정 (같은 날).** 별도 포트·데이터 폴더의 시험 서버에서 쓰기 모드 방(claude-fable-5-1·gpt-6-astra·gemini-3.8-flash, 모두 low)을 열었다. 그다음 "임시 PNG를 만들어 서버 scratch에 저장하고 첨부"하라고 요청했다.

- 1차(위 안내문): 세 좌석 모두 절대 경로를 썼다. 하지만 서버 scratch의 위치를 몰랐다. Fable은 Claude 자체 임시 폴더에, Flash는 Antigravity 자체 scratch에 저장해 2건이 거절됐다. Astra만 Codex 빌드 캐시 경로(`<scratch>/codex/go-build`)에서 위치를 추론해 성공했다. 거절 2건은 새 구조화 기록으로 각 모델에 정확히 귀속됐다.
- 원인: 안내문이 "서버 scratch"라는 이름만 쓰고 실제 경로를 주지 않았다. 파트는 추적하지 않는 파일이 남으면 제출이 거부되므로, 원래 사례의 Fable이 캡처를 scratch로 옮긴 것은 합리적인 선택이었다.
- 수정: `markerBrief`·`standingBrief`·`BuildPartPrompt`가 서버 scratch 절대 경로를 받아 안내문에 넣는다("서버 scratch 폴더 <경로> 의 파일은 절대 경로로", 쓰기 모드 예시 `[[ATTACH:<scratch>\캡처.png]]`). 다른 폴더는 거절된다고도 적었다.
- 2차(수정 후, 새 방): scratch 저장 첨부 3건과 작업 폴더 상대 경로(`shots/…`) 첨부 3건이 모두 처리됐다. 거절 알림은 0건이었다.
- 미확인: 작업 계획 파트(worktree) 안에서의 실제 CLI 흐름. 같은 `markerBrief`를 쓰고 단위 테스트로 파트 안내문의 경로를 확인했지만, 파트를 실제로 돌리지는 않았다.

공통: fallback·조용한 우회 금지, 계약 위반은 즉시 실패, 공개 레포이므로 내부 회사명·로컬 경로 금지, 커밋은 한국어.
