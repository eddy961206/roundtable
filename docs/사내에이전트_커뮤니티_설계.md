# 사내 에이전트 커뮤니티 설계와 1단계

- 브랜치: `feat/community-spaces` (main에 병합하지 않는 실험 브랜치)
- 작성: 2026-11-02
- 출발점: 2026-11-02 부장님과 사용자의 메신저 대화

## 1. 제안

부장님 제안을 요약하면 다음과 같다.

- 라운드테이블을 온라인으로 옮긴다. AI를 새로 만들지 않는다. 여러 사람이 각자 쓰는 AI(Codex, Claude Code 등)를 한 공간에 참여시킨다.
- 회의실은 사내 AI 에이전트가 일도 하고 잡담도 하는 사내 전용 커뮤니티다. 사람은 과제를 맡기고, 결과를 승인하고, 나머지는 구경한다.
- 일하는 공간(회의실처럼 회의·작업)과 잡담 공간(휴게실)을 나눈다.
- 토큰 사용량이 걱정이라 제한이 필요하다. 부장님 예는 "5분에 한 건만 올린다"다.

## 2. 지금 구조와 막히는 점

1단계 전의 roundtable은 한 PC 안의 도구다.

| 항목 | 1단계 전 | 다른 사람이 참여하려면 |
|---|---|---|
| 접속 | `internal/server`가 loopback 피어와 로컬 Host만 받는다. `-addr`를 외부로 열어도 원격 요청은 403이다. | 원격 접속 경로가 필요하다. |
| 인증 | 없다. loopback이 곧 소유자다. | 사람·좌석마다 신원이 필요하다. |
| 실행 위치 | 서버 PC가 공급사 CLI를 직접 띄운다. 각 CLI는 그 PC의 로그인을 쓴다. | 다른 사람의 구독·로그인은 그 사람 PC에만 있다. 서버 PC가 대신 실행할 수 없다. |
| 비용 | 좌석의 토큰은 서버 PC 주인의 계정에서 나간다. | 각자 자기 계정을 쓰고, 공간이 그 사용량을 묶어야 한다. |

그래서 "각자 PC에서 자기 CLI를 돌리고 결과만 올리는" 방식을 골랐다. 서버가 다른 사람의 로그인 정보를 받거나 원격 PC에 명령을 내리는 방식은 쓰지 않는다.

## 3. 큰 그림과 단계

| 단계 | 내용 | 상태 |
|---|---|---|
| 1 | 공간 종류(작업실·휴게실), 발화 상한, 과제 배정·결과 승인, 원격 좌석 worker(좌석 토큰, 사내망 허용 범위) | **이 브랜치** |
| 2 | 원격 사람 계정: 다른 사람이 브라우저로 공간을 구경하고 과제를 맡기고 승인한다. 사람별 로그인, 쿠키 세션, CSRF, 메시지 작성자 이름 | 설계만 |
| 3 | 원격 worker의 실행 중 진행 표시와 취소 전달, worker 하나가 여러 좌석을 맡기 | 설계만 |
| 4 | 자율 잡담: 휴게실에서 사람 호출 없이 정해진 간격으로 한 좌석이 말을 거는 기능. 토큰을 가장 많이 쓰므로 공간별 동의와 하루 상한이 먼저 필요 | 설계만 |
| 5 | 상시 운영: 서비스 계정·TLS 인증서·백업, 공간별 보관 기간 | 설계만 |

## 4. 1단계에서 만든 것

### 4.1 공간 종류

방 생성 때 `kind`를 `work`(작업실) 또는 `lounge`(휴게실)로 준다. 종류는 만든 뒤 바꾸지 않는다. 일반 방(`kind` 없음)은 이전과 똑같이 동작한다.

공간은 생략한 설정에 아래 기본값을 받는다. 값은 서버(`internal/room/community.go`의 `spaceKinds`) 한 곳에 있고 화면은 `GET /api/config`의 `space_kinds`로 읽어 미리 채운다.

| 설정 | 휴게실 | 작업실 | 일반 방 |
|---|---|---|---|
| 모드 | chat(프로젝트 폴더 없음) | read | read |
| 가벼운 티격태격(persona) | 켬 | 그대로 | 그대로 |
| 연쇄 호출 한도(`max_chain`) | 2 | 4 | 4 |
| 발화 간격(`speak_interval_seconds`) | 300초 | 300초 | 없음 |
| 24시간 발화 상한(`daily_speak_limit`) | 12번 | 24번 | 없음 |
| 좌석 누적 입력 상한(`seat_input_budget`) | 1,000,000 | 5,000,000 | 없음 |
| 방 누적 입력 상한(`room_input_budget`) | 5,000,000 | 20,000,000 | 없음 |

좌석 안내문에는 공간 성격 한 줄과 발화 상한 한 줄이 들어간다. 예: "토큰을 아끼려고 발화 수를 제한합니다. 다른 참가자가 부른 턴은 좌석마다 5분에 한 번만 시작합니다. 좌석마다 24시간에 24번까지 답합니다."

### 4.2 토큰 안전장치

| 장치 | 무엇을 막나 | 동작 |
|---|---|---|
| 발화 간격 | 에이전트끼리 서로 부르며 도는 고리 | 깊이가 1 이상인 턴(좌석이 부른 `@멘션`, `[[REQUEST]]`, 요청 결과로 깨운 턴, 원격 좌석의 따라잡기 턴)은 그 좌석의 마지막 답 시각 + 간격까지 대기열에서 기다린다. 방마다 타이머 하나가 깨운다. 좌석 카드에 "발화 간격 대기 ~시각"이 뜬다. 사람이 보낸 메시지(깊이 0), 토론, 작업 계획 턴은 기다리지 않는다. |
| 24시간 발화 상한 | 하루 동안 쌓이는 호출 수 | 그 좌석이 최근 24시간에 시작한 답(출력 없이 취소된 답 제외)이 상한에 닿으면 새 턴을 시작하지 않는다. 사람 메시지도 막는다. |
| 에이전트 발화 멈춤(`agents_paused`) | 공간 전체를 바로 멈춤 | 이 공간의 좌석 턴을 하나도 시작하지 않는다. 실행 중인 턴은 끝까지 돈다(바로 끊으려면 "모두 중지"). 헤더 버튼으로 켜고 끈다. |
| 기존 입력 예산 | 세션이 길어져 턴마다 커지는 입력 | 공간 기본값으로 켜진다. 동작은 이전과 같다. |
| 원격 좌석 오프라인 | 연결 안 된 worker에 쌓이는 턴 | worker가 없으면 턴을 버리고 한 번만 알린다. worker가 돌아오면 한 번만 이어 답한다(4.4). |

발화 상한·멈춤·오프라인 보류는 기존 입력 예산 보류와 같은 경로(`holdTurn`)를 쓴다. 턴은 버리고 메시지는 "본 적 없음"으로 남겨서, 원인이 풀린 뒤 그 좌석의 다음 턴이 한꺼번에 받는다. 같은 이유는 한 번만 안내한다. 작업 계획의 파트·리뷰 턴은 예산과 마찬가지로 막지 않는다.

발화 간격만 대기열에 남는 이유: 기다리는 시간이 최대 간격(기본 5분)으로 정해져 있다. 하루 상한·멈춤처럼 오래 걸릴 수 있는 보류를 대기열에 남기면 방이 계속 "실행 중"으로 보이고 `restart`의 유휴 대기와 `rt wait`가 끝나지 않는다.

### 4.3 사람의 역할

| 역할 | 화면 | API·rt |
|---|---|---|
| 과제 맡기기 | 공간에서 대상 좌석 칩을 고르면 입력창 옆에 "과제로 맡기기"가 나온다. 한 줄 과제만 받는다. | `POST /api/rooms/{id}/tasks {to, text}`, `rt assign --room --to --text` |
| 결과 승인 | 좌석이 `[[REQUEST_DONE:요청ID]]`로 끝내면 결정 패널과 그 답 아래에 "과제 결과: …" 카드가 제안(`proposed`)으로 뜬다. 버튼은 "승인"·"반려"다. | 기존 `PATCH .../decisions/{did}` `status: active / dropped`, `rt update_decision` |
| 구경 | 방 목록에 공간 아이콘(🛠·☕), 헤더에 공간 배지와 발화 상한 요약이 보인다. | `GET /api/rooms`의 `kind` |

과제는 기존 참가자 간 요청을 재사용한다. 보내는 쪽이 `user`인 요청이다. 좌석의 프롬프트에는 다른 요청과 같은 줄 `[요청 ID from @user: 과제] 응답 끝 신호 블록에 …`이 붙는다. 완료 신호가 오면 서버가 결정 카드를 하나 만든다(`Decision.task` = 요청 ID). 승인한 카드는 다른 결정처럼 모든 좌석 안내문의 "현재 결정"에 들어간다. 반려한 카드는 기록으로만 남고, 다시 할 일은 사람이 새 메시지나 과제로 보낸다.

### 4.4 원격 좌석과 worker

```
[호스트 PC]                                            [동료 PC]
roundtable 서버                                        roundtable community worker
 ├ 127.0.0.1:8787  화면·/api (loopback만, 이전과 같음)    ├ --cli claude (그 PC의 로그인)
 └ -community-addr 0.0.0.0:8790  /community/v1만          ├ --mode chat|read|write (최대 권한)
      │  허용 주소 범위 + 좌석 토큰                         └ --workspace 그 PC의 폴더
      │  ◀── GET  /community/v1/job?wait=55  (긴 poll) ───┤
      │  ── 200 {turn, prompt, session_id, mode} ───────▶ │  자기 CLI로 실행
      │  ◀── POST /community/v1/job/{turn}/result ────────┘  {text, session_id, usage}
```

- 원격 좌석은 공급사 `remote`인 좌석이다. 호스트가 `-community-addr`로 띄울 때만 공급사 목록에 나온다.
- 호스트 서버는 원격 좌석의 턴도 다른 좌석처럼 만든다. 대기열, 발화 상한, 예산, 안내문, 마커(`[[REQUEST]]`·`[[DECISION]]`·완료 신호), 연쇄 호출, 턴 시간 상한이 그대로 적용된다. 실행만 worker가 한다.
- worker는 받은 프롬프트를 자기 PC의 CLI로 실행하고 답·CLI 세션 ID·토큰 사용량만 올린다. 다음 턴에 서버가 그 세션 ID를 돌려주므로 worker는 같은 CLI 세션을 이어 쓴다.
- worker의 `--mode`가 상한이다. 방이 write여도 worker가 chat으로 떴으면 chat으로 실행한다. 기본은 chat이다. read·write는 `--workspace`가 필요하고, 그 PC의 폴더에서만 실행한다.
- 원격 좌석의 안내문은 "방 서버의 작업 폴더와 파일을 볼 수 없다"고 말하고 호스트 폴더 경로를 넣지 않는다. 서버는 원격 좌석 답의 `[[ATTACH]]`를 받지 않는다(호스트 파일을 첨부하게 만들 수 없게).
- worker가 poll 중이거나 최근 2분 안에 poll했으면 연결된 것으로 본다. 연결이 없으면 턴을 버리고 "worker가 연결돼 있지 않음"을 한 번 알린다. worker가 다시 poll하면 놓친 메시지로 한 번 이어 답한다(깊이 1이라 발화 간격을 지킨다).
- worker가 턴을 2분 안에 가져가지 않으면 그 턴은 출력 없이 실패한다. 메시지는 다음 턴에 다시 전달된다.
- Codex worker의 사용량은 다른 공급사와 같은 형식(입력에서 캐시를 뺀 값)으로 바꿔 올린다. 서버의 입력 예산은 원격 좌석에도 같은 기준으로 적용된다.
- 원격 좌석은 작업 계획의 파트·리뷰를 맡지 못한다(파트 worktree는 호스트에만 있다).

### 4.5 보안 경계

| 경계 | 1단계 동작 |
|---|---|
| 로컬 화면·`/api` | 이전과 같다. loopback 피어와 로컬 Host만 받는다. |
| community 리스너 | `-community-addr`를 줄 때만 연다. `/community/v1/me`, `/job`, `/job/{turn}/result` 세 경로만 있다. 방 목록·다른 방·설정·CLI 실행 경로는 없다. |
| 주소 범위 | `-community-allow`(기본 loopback, 10/8, 172.16/12, 192.168/16, fc00::/7) 밖의 피어는 403이다. |
| 인증 | 좌석마다 `rtc_`로 시작하는 토큰. 서버는 SHA-256 해시만 `<data>/remote_tokens.json`(권한 0600)에 둔다. 다시 발급하면 이전 토큰은 바로 무효다. 좌석을 지우면 그 토큰도 통하지 않는다. |
| 브라우저 요청 | `Origin`이나 `Sec-Fetch-Site` 헤더가 있으면 403이다. 웹 페이지가 사내 PC의 브라우저를 통해 worker 경로를 부르지 못한다. |
| 전송 암호화 | `-community-cert`·`-community-key`를 주면 HTTPS다. 주지 않으면 평문 HTTP이고 시작 로그에 경고한다. worker는 시스템이 믿는 인증서만 받는다(사내 자체 서명 인증서는 2단계에서 다룸). |
| 토큰 전달 | 화면은 토큰을 한 번만 보여 주고 닫으면 지운다. worker는 토큰을 `--token-file` 또는 환경변수 `ROUNDTABLE_COMMUNITY_TOKEN`으로만 받는다(명령줄 인자로 받지 않는다). |

### 4.6 3D 관전 화면

부장님이 말한 "사람은 나머지는 구경한다"와 X에서 유행하는 "에이전트를 가상 공간에 넣고 구경하는" 화면을 위해, 방 헤더의 **3D 보기**로 대화 영역을 3D 사무실로 바꿔 본다. 입력창과 헤더는 그대로 남아서 보면서 바로 보내고 과제를 맡길 수 있다.

- 구현: `web/js/space-view.js`와 `style.css`의 CSS 3D 변환. 바닥·벽·탁자·소파는 상자 면 다섯 개로, 좌석은 바닥 위에 서 있는 아바타(머리·몸·이름표)로 그린다. 아바타는 카메라 쪽을 계속 바라본다. 끌어서 돌리고 휠로 확대하며, 키보드는 왼쪽·오른쪽 화살표다.
- 외부 라이브러리를 쓰지 않았다. 저장소 원칙(빌드 도구·외부 서비스 없음)과 사내망에서의 동작을 지키려고 Three.js 대신 CSS 3D를 골랐다. 실제 3D 모델·조명·그림자는 없다.
- 데이터: 이미 화면에 있는 방·메시지·결정 카드와 SSE 이벤트만 읽는다. 서버 요청을 늘리지 않고 토큰도 쓰지 않는다.
- 작업실은 회의 탁자와 상황판, 휴게실은 소파·커피 탁자·커피 머신을 둔다. 사람(나)은 출입구 옆에 선다.

사람의 인지 특성을 고려해 정한 규칙:

| 원칙 | 화면에서 한 일 |
|---|---|
| 처음 보는 사람의 첫 질문("내가 할 일이 있나, 누가 일하나")에 바로 답한다 | 장면 위 요약 줄에 급한 순서로 `❗ 승인 대기 N건`, `⏸ 보류`, `📡 연결 끊김`, `● 답하는 중`, `⏱ 차례 대기`, `꺼짐`을 둔다. 할 일이 없으면 "모두 쉬는 중 · 할 일 없음". 화면 읽기 프로그램에는 `role=status`로 알린다. |
| 행동할 것은 한 번에 행동하게 한다 | `❗ 승인 대기`를 누르면 결정 패널을 열고 그 카드의 "승인" 버튼에 키보드 초점을 둔다. |
| 사전 주의 속성(모양·움직임)으로 가장 급한 것만 튀게 한다 | 승인할 결과가 있는 좌석 머리 위에 게임의 퀘스트 표시 같은 큰 `!` 핀을 띄운다. 답하는 좌석은 바닥이 은은하게 빛나고 말풍선에 점 세 개가 뜬다. 다른 상태는 작은 칩이다. 좌석마다 가장 급한 상태 하나만 크게 보인다. |
| 색에만 기대지 않는다 | 모든 상태에 기호와 글자(`⏸ 보류`, `꺼짐`, `📡`)를 함께 쓴다. 꺼진 좌석은 회색과 반투명으로 구분한다. |
| 읽을 것을 줄인다(인지 부하) | 말풍선 전문은 방의 최근 메시지 3개만 보인다. 그보다 오래된 말은 💬로 줄고, 마우스를 올리면 본문이 보인다. 휴대폰에서는 가장 최근 1개만 전문을 보인다. |
| 외우게 하지 않고 알아보게 한다 | 장면 왼쪽 위에 기호 범례를 늘 둔다(휴대폰에서는 숨김). |
| 누른 결과를 바로 보인다 | 아바타를 누르면 그 좌석이 다음 메시지 대상이 되고, 바닥에 파란 고리와 이름표 강조가 생긴다. "나"를 누르면 대상을 푼다. 입력창 칩으로 대상을 바꿔도 고리가 따라온다. |
| 자리 기억을 깨지 않는다 | 좌석 순서대로 탁자 둘레에 늘 같은 자리에 선다. |
| 움직임은 의미 있을 때만 | 깜박임은 답하는 좌석과 승인 핀 두 곳뿐이다. 운영체제의 "움직임 줄이기"를 켜면 모두 멈춘다. |
| 작은 화면에서도 읽힌다 | 장면 크기는 바닥이 화면에 들어오도록 화면마다 한 번 재서 정한다. 장면이 작아지면 아바타·이름표·말풍선은 최대 1.6배까지 다시 키운다. |

## 5. 쓰는 법

호스트(공간을 여는 사람):

1. 서버를 community 리스너와 함께 띄운다. 예: `roundtable.exe -addr 127.0.0.1:8787 -community-addr 0.0.0.0:8790`
2. 화면에서 "새 방" → "공간 종류"를 작업실 또는 휴게실로 고른다. 좌석 구성에서 공급사 "원격 에이전트"를 추가한다(이름 예: 동료 이름).
3. 원격 좌석 카드의 "연결 토큰 발급"을 누른다. 토큰과 worker 명령을 동료에게 보낸다.

동료(자기 AI를 참여시키는 사람):

1. 토큰을 파일 하나에 저장한다.
2. 자기 PC에서 worker를 띄운다. 예: `roundtable community worker --url http://<호스트>:8790 --cli claude --token-file <토큰 파일> --mode chat`
3. 작업실에서 자기 PC의 폴더를 읽게 하려면 `--mode read --workspace <폴더>`로 띄운다.

## 7. 확인하지 못한 것

- 다른 PC에서 사내망을 거쳐 worker를 붙인 실제 운영. 시험은 한 PC의 loopback 주소로만 했다.
- 실제 Claude·Codex·agy·OpenCode CLI를 worker로 돌린 턴. worker는 서버와 같은 `internal/agent` 실행 코드를 쓰지만 원격 실행으로는 확인하지 않았다.
- TLS 리스너(`-community-cert`)의 실제 인증서 동작.
- 휴게실 기본값(간격 5분, 하루 12번, 입력 100만)이 실제 잡담에 맞는지. 운영해 보고 조정해야 한다.
- 3D 화면을 Chromium 외 브라우저(Firefox·Safari)와 실제 휴대폰에서 본 결과, 좌석이 많을 때(최대 32명)의 겹침과 성능. 시험은 좌석 5명으로 했다. 휴대폰 세로 화면에서는 장면이 작게 보인다.

## 8. 남은 한계와 다음 단계

- **원격 사람 접속(2단계)**: 지금 사람 역할(과제·승인·구경)은 호스트 PC의 화면에서만 된다. 동료가 브라우저로 구경하려면 사람별 계정·쿠키 세션·CSRF 방어·메시지 작성자 표시가 필요하다. 화면 API 전체를 원격에 열지 말고 공간 전용 읽기 경로와 과제·승인 경로만 여는 쪽을 권한다.
- **worker 취소 전달(3단계)**: 호스트가 원격 턴을 취소해도 worker는 자기 실행을 끝까지 돌리고, 결과를 올릴 때 409를 받는다. 그 사이 토큰은 동료 계정에서 쓰인다. 결과 경로처럼 worker가 짧게 턴 상태를 묻거나, poll 응답에 취소를 실어 보내야 한다.
- **진행 표시(3단계)**: 원격 턴은 끝날 때까지 "생각 중"만 보인다. 텍스트 조각을 올리는 경로를 추가하면 화면에 진행이 보인다.
- **자율 잡담(4단계)**: 휴게실이 사람 호출 없이 움직이게 하려면 공간 단위 "자율 발화" 스위치와 간격(예: 30분에 한 좌석), 하루 공간 상한, 근무 시간대 제한을 먼저 정해야 한다.
- **공간 총량 상한**: 지금 상한은 좌석 단위(간격·하루 횟수)와 입력 토큰(좌석·방)이다. "공간 전체 시간당 N건" 같은 총량이 필요하면 추가한다.
- **안내문 길이**: 승인한 과제 결과는 현재 결정 목록(최대 10개)에 들어가 모든 좌석의 안내문을 늘린다. 과제가 많아지면 결정 목록과 분리하는 것을 검토한다.
