# 방 메시지 기록의 메모리 측정과 판단 (2026-11-03)

서버는 시작할 때 모든 방의 `messages.jsonl`을 읽어 `roomState.msgs`에 넣는다. 켜져 있는 동안 새 메시지도 계속 덧붙인다. 이 기록을 "최근 N개만 메모리, 나머지는 파일에서 읽기"로 바꿀지 측정으로 판단했다.

**결론: 지금은 바꾸지 않는다.** 현재 실사용 규모에서 기록이 차지하는 힙은 수 MB로 추정되고, 최근 N개 방식은 메시지 전달 계약을 포함한 15곳 이상을 다시 짜야 한다. 생산 코드는 바꾸지 않았고, 측정 도구(`internal/room/history_memory_test.go`)만 추가했다. 그래서 "변경 후" 측정값은 변경 전과 같다.

## 측정 방법

- 도구: `go test ./internal/room -run '^$' -bench BenchmarkHistory -benchtime=3x -count=3`
- 데이터: 임시 폴더의 방 하나에 합성 메시지 1만·10만 개를 `messages.jsonl`로 직접 쓰고, 새 `Hub`가 서버 시작과 같은 경로(`NewHub` → `loadRooms`)로 읽는다. 사람 메시지(300바이트) 1개마다 좌석 답변(2,000바이트, 사용량 map·timing 포함) 2개를 둔다. CLI·모델은 실행하지 않는다.
- `live-MB`: 읽기 전후 각각 GC를 두 번 돌린 뒤의 `HeapAlloc` 차이다. 할당량(`B/op`)과 다른 지표다.
- 환경: Windows 11, Intel i7-1355U, Go 1.27.2. 아래 시간은 3회 실행의 중앙값이다. 다른 작업을 통제하지 않았으므로 시간은 경향만 본다.
- 실사용 데이터(`~/.roundtable`)는 파일 크기·줄 수·메시지 ID 개수·`archived` 여부만 읽었다. 내용은 복사하지 않았고 127.0.0.1:8787 서버에는 접속하지 않았다.

## 결과

| 메시지 수 | 파일 크기 | 읽은 뒤 남는 힙 | 메시지당 힙 | 시작 시 읽기 |
|---|---|---|---|---|
| 10,000 | 16.65 MB | 23.2 MB | 2,432 B | 85 ms |
| 100,000 | 166.7 MB | 231.9 MB | 2,432 B | 768 ms |

힙은 메시지 수에 정비례하며, 파일 크기의 약 1.39배다.

| 작업 (방 하나) | 1만 개 | 10만 개 | 비고 |
|---|---|---|---|
| 첫 화면 `SnapshotJSON` (최근 100개) | 0.43 ms | 1.65 ms | 증가분은 전체 질문 목록(`askViews`) 순회 |
| 좌석 전달 `deltaFor` (밀린 10개) | 0.05 ms | 1.45 ms | 매 턴 1회 |
| 질문 목록 `askViews` | 0.05 ms | 1.29 ms | Snapshot마다 |
| 사용량 화면 `RoomUsage` | 0.79 ms | 11.7 ms | 요청할 때만 |

### 실사용 규모 (2026-11-03 관측)

- 방 160개, `messages.jsonl` 합계 7.57 MB, 2,386줄, 고유 메시지 1,131개. 가장 큰 방은 0.40 MB다. 같은 메시지가 상태 변화마다 다시 기록되므로 줄 수가 메시지 수보다 많다.
- 보관한 방은 14개, 0.84 MB(11%)다. 보관한 방만 내리는 방식으로는 큰 이득이 없다.
- 기록이 차지하는 힙은 **약 3–11 MB로 추정**한다. 하한은 고유 메시지 수 × 합성 메시지당 힙이고, 상한은 전체 파일 크기 × 1.39다. 실제 값은 실사용 서버를 건드리지 않으려고 재지 않았다.
- 같은 시각 `roundtable` 프로세스 2개의 private memory는 47 MB, 68 MB였다. 어느 프로세스가 8787인지는 확인하지 않았다.
- 가장 오래된 방 폴더가 2026-10-20이다. 14일 동안 고유 메시지 1,131개(하루 약 80개)가 쌓였다. 이 속도가 유지된다는 가정에서 전체 1만 개(약 23 MB)는 약 4개월 뒤, 10만 개는 약 3년 뒤다.
- 휴게실 자율 잡담은 사람이나 다른 답변 없이 3줄(`autoChatStreak`)까지만 이어진다. 그래서 사람 활동 없이 기록이 무한히 늘지는 않는다.

## 최근 N개 방식이 바꿔야 하는 곳

`rs.msgs`는 화면용 캐시가 아니라 방 상태의 원본이다. 아래 기능은 오래된 메시지가 메모리에 있다고 가정한다.

| 기능 | 위치 | 오래된 메시지가 필요한 이유 |
|---|---|---|
| 좌석 전달 | `deltaForContext` (hub.go) | 새 세션의 첫 턴은 `HistoryFrom` 이후 전체를 받는다. 오래 꺼 둔 좌석은 `LastSeen` 이후를, 끝나지 않은 답은 `Unseen` 구멍을 나중에 받는다. |
| 질문 | `askViews`, `closeAsks`, `AnswerAsk`, `countOpenAsks` (asks.go) | Snapshot이 방의 모든 질문을 돌려주고, 오래된 열린 질문도 닫고 답할 수 있다. |
| 첨부 중복 검사 | `resolveAttachments` (attachments.go) | 이미 붙은 첨부 ID를 전체 기록에서 찾는다. 시작 시 `cleanupAttachments`도 전체를 본다. |
| 사용량 | `RoomUsage` (stats.go), `backfillInput` (budget.go), `sessionCost` (hub.go) | 좌석별 합계를 전체 답변에서 다시 센다. 세션 비용은 같은 세션의 마지막 답변에서 읽는다. |
| 결정·요청 | `activeDecisionTexts` (decisions.go), `pendingRequests`, 요청 처리 (requests.go) | 출처 메시지의 seq와 멘션을 ID로 찾는다. 출처는 오래된 메시지일 수 있다. |
| 메시지 지정 작업 | `Forward`, `ApplyMarkers`, `checkTraceMessage`, CLI 열기 (native.go), 턴의 `ReplyTo` | 사용자가 고른 seq·ID의 메시지를 찾는다. |
| 기록 페이지 | `snapshotLocked` (history.go) | 위로 스크롤하면 `before` 이전 페이지를 같은 slice에서 자른다. |
| 공간 | `lastReplyAt`, `repliesSince`, `autoStreak` (community.go) | 뒤에서부터 찾고 시간 범위에서 멈춘다. 최근 N개로도 대부분 맞지만, 오래 말하지 않은 좌석의 `lastReplyAt`은 오래된 메시지를 본다. |

이 목록을 최근 N개로 바꾸려면 질문·첨부·사용량은 별도 색인이나 누적값으로, 전달·메시지 지정·기록 페이지는 파일 offset 색인 읽기로 바꿔야 한다. 한 곳이라도 놓치면 빈 기록을 정상처럼 쓰는 조용한 오류가 생긴다. 지금의 수 MB 절감과 비교하면 회귀 위험이 더 크다.

## 다시 판단할 조건

- 전체 고유 메시지가 약 4만 개(추정 힙 100 MB)를 넘거나, 한 방이 2만 개를 넘을 때 이 측정을 다시 돌린다.
- 그때는 메시지 전체를 내리기보다 메모리를 가장 많이 쓰는 `Text`만 offset 색인으로 내리는 방식을 먼저 검토한다. 합성 데이터에서 본문은 메시지당 평균 1,433바이트로, 메시지당 힙 2,432바이트의 약 60%다. 다만 `deltaFor`·`Forward`·기록 페이지가 본문을 읽으므로 그 세 경로의 파일 읽기는 여전히 필요하다.

## 남은 한계

- 합성 메시지 크기는 실사용 평균 줄 크기를 참고했지만, 실제 메시지의 크기 분포·사용량 map 모양과 다를 수 있다.
- 실사용 서버의 실제 힙은 재지 않았다. 위 3–11 MB는 추정이다.
- 장시간 켜 둔 서버의 GC 이후 RSS 변화(Go가 OS에 메모리를 돌려주는 시점)는 측정 범위 밖이다.
