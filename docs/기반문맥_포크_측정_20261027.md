# 기반 문맥 포크 A/B 실측 (2026-10-27)

[기반문맥_포크_계약.md](기반문맥_포크_계약.md)의 기능을 "작업마다 새 방"과 비교했다.

## 무엇을 비교했나

- **새 방(fresh)**: 작업마다 방을 새로 만든다. 작업 지시 앞에 "공통 문서 6개를 끝까지 읽으라"는 문장을 붙인다. 지금까지 오케스트레이터가 쓰던 방식이다.
- **포크(fork)**: 기반 방 하나에서 같은 문서를 읽히고 "준비됨"만 받는다. 작업마다 방을 새로 만들되 좌석에 `fork_from`으로 기반 좌석을 지정하고, 작업 지시만 보낸다.
- 공통 문서: 이 저장소의 README.md, 계약 문서 4개, `skills/roundtable/SKILL.md` (합계 73,926바이트).
- 작업 3개, 모두 읽기 모드: (1) 역할 카드 규칙 하나를 구현과 대조, (2) `rt read` `max_chars` 설명을 구현과 대조, (3) 결정 카드 상태에 관한 틀린 주장을 검수. 각각 "결론 한 문장과 근거(파일:줄) 두 개"만 답한다.
- 작업 폴더: 측정 시점 커밋을 별도 폴더에 고정한 사본. 시험 서버는 별도 포트·별도 데이터 폴더로 띄웠다.
- 두 방식을 같은 서버에서 동시에 돌렸다(계정·모델·시각이 같다). 같은 시나리오를 2회 반복했다. 1회차 시작 10:41, 2회차 10:45 (KST).
- 스크립트: `tools/token_ab/fork_tasks.py`(실행), `tools/token_ab/fork_summary.py`(표).

수치의 뜻:
- Codex: **비캐시 입력** = `input_tokens − cached_input_tokens`, **캐시 입력** = `cached_input_tokens`. 둘 다 그 답변 한 턴의 모든 모델 호출 합이다.
- Claude: **비캐시 입력** = `input_tokens + cache_creation_input_tokens`, **캐시 입력** = `cache_read_input_tokens`, 비용은 CLI가 보고한 그 턴의 USD.
- 도구 호출은 그 턴의 작업 기록에 남은 `tool_call` 수, 시간은 턴 시작부터 끝까지다.

## 결과 1 — Codex gpt-6.1-sol high

작업 1개 평균(2회 × 3작업 = 6개):

| 항목 | 새 방 | 포크 | 차이 |
| --- | ---: | ---: | ---: |
| 비캐시 입력 | 58,567 | 41,537 | **−29%** |
| 캐시 입력 | 206,955 | 108,160 | **−48%** |
| 출력 | 1,198 | 416 | −65% |
| 도구 호출 | 13.2 | 2.5 | −81% |
| 시간 | 51.5초 | 23.3초 | −55% |

기반 방 1회(2회 평균): 비캐시 41,745, 캐시 176,384, 출력 568, 도구 호출 12, 36초.

작업 3개 + 기반 1회 합계:

| 회차 | 비캐시 입력 새 방 → 포크 | 캐시 입력 새 방 → 포크 | 시간 새 방 → 포크 |
| --- | --- | --- | --- |
| 1 | 151,661 → 153,285 (+1%) | 624,256 → 500,352 (−20%) | 167초 → 113초 |
| 2 | 199,741 → 179,428 (−10%) | 617,472 → 501,376 (−19%) | 142초 → 98초 |

- 손익분기점: 비캐시 입력은 작업 약 2.5개, 캐시 입력은 약 1.8개다(기반 비용 ÷ 작업당 절감량). 작업이 3개를 넘으면 포크가 모든 항목에서 적다.
- **포크의 첫 호출은 Codex 캐시를 대부분 쓰지 못한다.** 포크 rollout을 호출 단위로 보면 첫 호출 입력 약 52,000 중 캐시는 12,288~19,584뿐이고, 두 번째 호출부터는 거의 전부 캐시다. 같은 기반 thread를 `codex exec resume`으로 이으면 첫 호출도 99% 캐시였다(아래 사전 확인). 캐시가 thread별로 나뉘는 것으로 보이며, CLI에 이를 바꾸는 옵션은 찾지 못했다(`codex exec fork --help`, Codex 0.162.1). 그래서 Codex 포크는 작업마다 기반 문맥 크기만큼을 한 번 비캐시로 보낸다. 비캐시 절감이 −29%에 그치는 이유다.
- 절감은 주로 문서를 읽는 도구 호출(작업당 약 10회)과 그 호출마다 다시 보내던 누적 문맥에서 나온다.

## 결과 2 — Claude claude-sonnet-5-5 medium

작업 1개 평균(6개):

| 항목 | 새 방 | 포크 | 차이 |
| --- | ---: | ---: | ---: |
| 비캐시 입력 | 34,283 | 2,606 | **−92%** |
| 비용(USD) | 0.159 | 0.029 | **−82%** |
| 도구 호출 | 5.0 | 1.2 | −76% |
| 시간 | 19.2초 | 15.0초 | −22% |

기반 방 1회(2회 평균): 비캐시 49,736, 비용 0.212 USD, 17초.

| 회차 | 비용 새 방 → 포크(기반 포함) | 비캐시 입력 새 방 → 포크(기반 포함) |
| --- | --- | --- |
| 1 | 0.409 → 0.318 (−22%) | 85,479 → 61,227 (−28%) |
| 2 | 0.544 → 0.282 (−48%) | 120,217 → 53,884 (−55%) |

- Claude 포크는 첫 호출부터 기반 문맥 전체(약 108,000)가 캐시에서 읽힌다. Anthropic 캐시는 같은 접두부면 세션이 달라도 맞는다.
- 비용 손익분기점은 작업 약 1.6개다.
- **새 방의 Claude는 문서를 다 읽지 않은 경우가 많았다.** 6개 중 3개는 도구 호출이 1~4회였다(지시는 "모두 끝까지 읽으라"). 문서를 실제로 읽은 새 방 작업은 0.236~0.259 USD였다. 그래서 위 표의 새 방 평균은 실제 읽기 비용보다 낮다.

## 답의 정확성

12개 작업 답 모두 결론이 맞았다(작업 1·2는 "지킨다/일치한다", 작업 3은 "틀렸다, 카드는 proposed로 생기고 확정해야 안내문에 들어간다"). 포크 좌석은 문서를 다시 읽지 않고 계약 문서의 줄 번호를 인용했다. 근거 줄 번호가 정확한지까지는 하나씩 대조하지 않았다.

## 사전 확인 (CLI 직접 실행, 같은 날)

| 확인 | 결과 |
| --- | --- |
| Codex `codex exec fork <id> -` | 새 thread id로 시작하고 기반 내용을 기억한다. `turn.completed` 누적값에 기반 thread 사용량이 들어 있고, 포크 rollout에는 기반의 token_count가 없다(계약 F7의 근거). 첫 호출 캐시 12,288 / 26,268. |
| Codex `codex exec resume <id> -`(비교) | 같은 질문의 첫 호출 캐시 26,112 / 26,268. |
| Claude `--resume <id> --fork-session` | 새 세션 id. 캐시 읽기 93,470, 새 입력 305. `total_cost_usd`가 기반 세션 누적 비용을 포함한다(같은 세션 재개와 증가량이 같음, 계약 F7의 근거). |
| OpenCode `--session <id> --fork` | 새 세션 id로 기반 내용을 기억했다(`roundtable rt`로 확인, 무료 모델). |
| agy | 포크 옵션 없음(`agy --help`, 1.4.7). 생성 요청을 거절한다. |

## 한계

- 작업이 작다. 실제 작업은 문서를 읽은 뒤 도구 호출이 수십 번 이어지고, 그 비용은 포크와 상관없이 같다. 포크가 줄이는 것은 **작업마다 반복되던 문서 읽기 단계**다. 작업당 절감량(Codex 기준 비캐시 약 17,000, 캐시 약 99,000, 도구 호출 약 10회, 약 28초)은 작업 크기와 상관없이 비슷하고, 공통 문서가 클수록 커진다.
- 각 방식 2회만 반복했다. Codex 새 방의 작업당 비캐시는 회차에 따라 50,554와 66,580으로 차이가 컸다.
- 기반 문맥이 크면 Codex 포크의 첫 호출 비캐시도 그만큼 커진다. 기반 방에는 작업을 보내지 않아야 한다.

## 추가 측정 — agy 검수 좌석 이어 쓰기 (같은 날 12시경)

agy는 포크가 없어서, 검수 좌석 하나를 계속 쓰는 방식("이어 쓰기")과 검수마다 새 방을 만드는 방식("새 좌석")을 비교했다.

- 모델: gemini-4-argon high, 읽기 모드, 같은 저장소 사본.
- 검수 6건: `internal/room`의 소스 파일 6개(8~17KB)를 한 건에 하나씩 읽고 "확인한 사실 한 가지와 의심 지점 한 가지"를 두 줄로 답한다. 두 방식을 동시에 돌렸고, 매 건은 `roundtable rt wait`으로 기다렸다.
- 스크립트: `tools/token_ab/agy_reuse.py`. 1회만 측정했다.
- 수치: agy의 `input_tokens`는 비캐시 입력, `cache_read_tokens`는 캐시 입력, `context_tokens`는 그 턴 마지막 호출의 입력 전체다.

| 검수 | 이어 쓰기 비캐시 | 이어 쓰기 캐시 | 이어 쓰기 문맥 | 새 좌석 비캐시 | 새 좌석 캐시 | 새 좌석 문맥 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1 | 14,314 | 9,443 | 14,315 | 14,371 | 9,447 | 14,372 |
| 2 | 8,203 | 32,653 | 22,520 | 14,099 | 9,447 | 14,100 |
| 3 | 9,249 | 48,811 | 31,771 | 15,570 | 9,445 | 15,571 |
| 4 | 7,525 | 66,900 | 39,298 | 14,024 | 9,454 | 14,025 |
| 5 | 9,121 | 81,888 | 48,421 | 16,237 | 9,454 | 16,238 |
| 6 | 9,663 | 100,118 | 58,086 | 16,509 | 9,445 | 16,510 |
| 합계 | 58,075 | 339,813 | | 90,810 | 56,692 | |

- 출력 합계는 이어 쓰기 16,958, 새 좌석 21,570이었다. 시간 합계는 258초와 301초였다.
- **이어 쓰기는 두 번째 검수부터 비캐시 입력이 약 40% 적다.** 이전 검수의 문맥이 캐시로 읽히기 때문이다.
- **대신 문맥이 검수마다 약 8,700씩 커지고, 캐시 입력은 검수마다 약 18,000씩 늘었다.** 한 검수 안의 모든 모델 호출이 쌓인 문맥 전체를 다시 보내기 때문이다. 6건 합계 캐시 입력은 새 좌석의 6배였다.
- 캐시 입력 단가가 비캐시의 25%라고 가정하면(가정, 공급사 단가는 확인하지 않음) 6건 합계는 이어 쓰기 약 143,000, 새 좌석 약 105,000(비캐시 환산)이다. 10%라고 가정하면 약 92,000과 96,000으로 비슷하다. 검수가 쌓일수록 이어 쓰기가 불리해진다.
- 실제 검수는 이 시험보다 훨씬 크다. 방 기록을 보면 실제 Argon 검수 좌석은 첫 검수 하나로 문맥이 약 142,000이었다. 이런 좌석을 이어 쓰면 다음 검수의 모든 호출이 그만큼을 다시 보낸다.
- 이전 실측([토큰절감_측정_20261020.md](토큰절감_측정_20261020.md)): agy는 재개 턴마다 약 1,000토큰을 스스로 붙이고, 추론 수준을 바꾸면 그 턴은 문맥 전체를 비캐시로 다시 읽는다. 방 기록에서 gemini-3.8-flash 좌석은 문맥이 약 254,000에 이르자 다음 턴에 약 103,000으로 줄었다(CLI의 자동 압축으로 보임). gemini-4-argon의 문맥 창은 1,048,576이다.
