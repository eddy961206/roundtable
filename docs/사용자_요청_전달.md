# 좌석의 사용자 요청 전달

대상: `fix/user-request`, 기준 `383e02d`. 운영 서버와 기존 방은 변경하지 않습니다.

## 설계

- 사용자 요청은 좌석 간 `Request` 및 턴 중 질문 `Ask`와 수명이 다릅니다. 다음 턴이 시작돼도 `pending`을 유지하고, 사람이 답하면 `answered`, 확인 표시하면 `acknowledged`로 닫습니다.
- 이미 저장되는 `notice_marker=user_request` 공지를 요청의 원본으로 씁니다. 공지 메시지 ID가 요청 ID, 공지 seq가 알림 순서입니다. 별도 저장 파일이나 기존 좌석 요청 스케줄러는 추가하지 않습니다.
- 답변 또는 확인 메시지에 요청 ID와 처리 내용을 함께 저장합니다. 메시지 하나의 append가 처리 경계입니다. 재기동할 때 공지와 처리 메시지로 상태를 복원합니다. 옛 공지도 같은 형식으로 복원하며, 과거 산문만 보고 처리 여부를 추측하지 않습니다. 따라서 예전에 수동 처리한 공지는 한 번 확인 표시해야 할 수 있습니다.
- `rt wait`의 `rooms`는 `방:after_seq[:user_request_seq]`를 받습니다. 세 번째 값은 이미 전달받은 사용자 요청의 공지 seq입니다. 생략하면 0이므로 대기 전에 생긴 미처리 요청도 알립니다. `user_requested:true`, `user_requests[]`에 내용과 상태를 반환합니다.
- 결과의 `waiting`을 다음 호출에 그대로 사용합니다. 세 번째 값이 포함되므로 미처리 요청이 남아도 같은 알림으로 반복 반환하지 않습니다. 신규 요청은 다시 깨웁니다. 이는 호출자의 수신 위치이며 서버의 처리 상태를 바꾸지 않습니다. 호출 결과를 잃었거나 새 오케스트레이터가 시작하면 커서 없이 다시 읽을 수 있습니다.
- `asked`의 기준과 방 완료 판정은 그대로 둡니다. `max_chars`와 `summary`는 요청 내용을 줄이지 않습니다.
- `rt resolve_user_request --room --id (--text "답" | --acknowledge true)`를 추가합니다. 답은 원래 요청한 좌석 ID로만 보내며 일반 대상 지정 메시지의 전달 규칙을 재사용합니다. 실행 중이면 공급사의 기존 steering 지원에 따라 전달하거나 대기열에 넣고, 대기 중이면 기존 대상 메시지 우선순위를 지킵니다. 끝난 좌석에는 새 턴을 만듭니다. 확인 표시는 좌석을 깨우지 않습니다. 좌석 비활성·삭제 등으로 답을 보낼 수 없으면 오류를 반환하고 요청은 미처리로 남깁니다.
- HTTP는 `POST /api/rooms/{id}/user-requests/{rid}/resolve`에 `{text}` 또는 `{acknowledge:true}`를 받습니다. 답변일 때는 결과의 `seq`로 새 답을 기다릴 수 있습니다. 확인 표시의 `seq`는 처리 기록 번호이며 새 답을 만들지 않으므로 기존 `waiting`을 이어 사용합니다. 기존 발화 멈춤·예산 제한은 유지됩니다. `answered`는 답변 접수이며 좌석의 처리 완료를 보증하지 않습니다.
- discussion·review의 새 요청 금지, 파트에서의 사용자 요청, 고유하게 일치하는 활성 좌석을 우선하는 판정은 기존 `requestTarget` 경계를 유지합니다.

## 범위와 한계

- 운영 `127.0.0.1:8787` 및 지정된 기존 방에는 시험 요청을 보내지 않았습니다. 운영 PID `27196`의 시작 시각은 조사 전후 모두 `2026-11-06 11:30:46 KST`였습니다. 운영 서버 배포·main 병합·push·PR은 이번 작업에 포함하지 않습니다.
- 실제 실행 검증은 Codex 한 좌석입니다. 다른 공급사의 실제 steering은 실행하지 않았으며, 전달 분기는 제어 가능한 공급사 시험으로 확인했습니다.
- 별도 `roundtable-codex-steer` 변경과 합친 상태는 검증하지 않았습니다. 이 브랜치는 기준 커밋의 기존 전달 규칙을 재사용합니다.
- 옛 산문 답변의 의미는 자동 판정하지 않습니다. 옛 공지 중 이미 처리한 건은 사람이 확인 표시해야 합니다.
- 모델 검사는 명시한 유한 범위의 동시성 검사이며 전체 프로그램 증명이 아닙니다.
