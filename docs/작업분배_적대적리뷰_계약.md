# 작업 분배·적대적 리뷰 계약 (v1)

2026-10-19 설계 방(Opus·Astra·Argon) 토론과 오케스트레이터 결정을 묶은 구현 계약이다. 세 파트는 이 문서와 `internal/room/work_types.go`, `internal/room/review_types.go`의 이름을 그대로 쓴다. 계약을 바꿔야 하면 구현하지 말고 먼저 방에 알린다.

## 1. 무엇을 만드는가

- **작업 분배**: write 방에서 사람이 "작업 계획"을 확정하면, 파트마다 담당 좌석이 같은 기준 커밋에서 만든 자기 worktree·branch에서만 작업한다.
- **적대적 리뷰**: 파트를 제출하면 작성자와 다른 공급사 좌석이 diff만 보고 고정 형식 표로 지적한다. 작성자는 항목별로 수용 또는 반박하고, 리뷰어는 반박 항목을 유지 또는 철회한다. 수용 항목은 수정 후 새 SHA에서 다시 확인한다.
- **병합**: 리뷰를 통과한 파트는 방 전용 통합 branch로 병합한다. 병합 토글은 방(계획)마다 하나다.
  - `auto`(자동모드): 사람 승인 없이 병합한다.
  - `confirm`(확인모드): 사람이 승인 버튼을 눌러야 병합한다.
  - 충돌·검증 실패·미해결 이견은 두 모드 모두 멈추고 사람에게 보여 준다. 조용히 우회하지 않는다.

## 2. 결정 (D1~D13)

| 번호 | 결정 |
| --- | --- |
| D1 | 병합 대상은 전용 통합 branch `rt/<방ID>/integration`이다. main 반영은 사람이 따로 한다. |
| D2 | 사용자 checkout을 건드리지 않는 통합 worktree(detached HEAD)에서 `--no-ff` merge commit을 만들고 verify를 돌린다. rebase는 쓰지 않는다. |
| D3 | 교차 리뷰는 두 모드 모두 필수다. 파트마다 리뷰어는 작성자와 `Provider`가 다른 활성 좌석이다. 없으면 계획 확정이 실패한다. |
| D4 | 미해결 항목(`open`, `accepted_pending`, `disputed`)이 하나라도 남으면 심각도와 상관없이 병합하지 않는다. |
| D5 | 병합 대기열은 방마다 FIFO, 한 번에 하나다. 어느 파트든 `blocked`가 되면 `Halted`가 설정되어 대기열 전체가 멈춘다. |
| D6 | 토글은 파트가 병합 준비(`queued`)에 도달한 순간의 값을 `ReadyMode`로 고정한다. 승인은 `SubmitSHA`와 `IntegrationSHA`에 묶이며 둘 중 하나가 바뀌면 무효다(서버 409). |
| D7 | 파트 분할은 사람이 계획 폼에서 확정한다. 에이전트 제안 자동 파싱은 v1에서 뺀다. |
| D8 | 새 방 mode를 만들지 않는다. write 방에 계획이 있으면 켜지는 워크플로다. |
| D9 | 파트 작업은 좌석의 채팅 세션과 분리된 `Part.SessionID`를 쓴다. 좌석에 `working`·`fixing` 파트가 있는 동안 그 좌석의 모든 턴은 파트 세션·파트 worktree로 실행한다. 파트 세션 첫 턴에는 계획·파트 정보만 넣고 방 대화 이력은 넣지 않는다. 파트가 `merged`·`abandoned`가 되면 채팅 세션으로 돌아간다. |
| D10 | 리뷰어 턴은 매번 새 세션이다. 대화 이력 없이 목표·파트 범위·base/head SHA·diff·이전 라운드 구조화 기록만 준다. 작성자 응답 턴은 파트 세션을 쓴다. |
| D11 | 표 파싱은 엄격하다. 형식이 틀리면 그 턴을 error로 끝내고 부분 결과를 채택하지 않는다. 채팅에는 원문 말풍선과 요약 system 한 줄을 남기고, 보드는 구조화 상태만 표시한다. |
| D12 | Diff는 파일 목록·추가/삭제 줄 수·파일별 patch를 서랍에서 지연 로드한다. |
| D13 | 상태는 `room.json`의 `work`에 저장하고 SSE `work` 이벤트로 전체 view를 보낸다. 상태 변화는 system 메시지로 남긴다. 병합 순서와 재시작 복구는 §5를 따른다. |

## 3. 상태 기계 (파트)

```text
working ──submit──▶ reviewing ──(passed)──▶ queued ──▶ awaiting_approval ──approve──▶ merging ──▶ merged
   ▲                    │  ▲                   │ (ReadyMode=auto이면 건너뜀)          │
   │                    │  └──resubmit──┐      │                                      │
   │               (fix)▼               │      ▼                                      ▼
   └──────────────── fixing ────────────┘   blocked{kind, from} ◀────────────── (실패 전부)
                                              │ retry → from 상태로, abandon → abandoned
```

- `submit`은 에이전트 신호 `WORK:DONE`(응답 마지막 줄) 또는 사람의 제출 버튼으로 시작하며 둘 다 `SubmitPart` 검사를 거친다.
  - 커밋하지 않은 변경·추적하지 않는 파일이 없어야 한다.
  - `BaseSHA`보다 앞선 커밋이 1개 이상 있어야 한다.
  - 실패하면 `blocked{kind:"submit"}`.
- 리뷰 결과 `fix`이면 `fixing`으로 가고 작성자가 수정 후 다시 제출한다(`resubmit`). 새 SHA로 재리뷰한다.
- 리뷰 결과 `disputed` 또는 `limit`이면 `blocked{kind:"review"}`.
- `Block.Kind`: `worktree` | `submit` | `conflict` | `verify` | `review` | `restart`.

## 4. 리뷰 흐름 (Astra 소유: `review.go`)

hub는 리뷰 내부 규칙을 모른다. `ReviewState`가 다음 단계(누가, 어떤 프롬프트)를 알려 주고, hub는 그 턴을 실행해 응답을 돌려준다.

```go
step, err := part.Review.Start(in)          // 첫 제출: reviewer 단계
next, outcome, err := part.Review.Apply(reply) // 턴 응답 반영
step, err := part.Review.Resubmit(in)       // fixing 후 새 SHA 제출
```

- `ReviewStep.Who`: `reviewer`(새 세션) | `author`(파트 세션).
- `Apply`의 `outcome`: `""`(next 단계 실행) | `fix` | `passed` | `disputed` | `limit`.
- 라운드: 초기 리뷰 = 1, 수정 SHA 재리뷰마다 +1. 반박·유지/철회는 같은 라운드다. 상한은 `WorkPlan.ReviewRounds`(입력 경계 기본 3). 상한을 넘기면 `limit`.
- `passed`는 리뷰 통과만 뜻한다. 병합 가능 여부는 hub가 D4·D6으로 판단한다.

### 표 형식 (모델 출력 계약)

표는 별도 라벨 없이 머리글 행으로 식별한다. 열 이름과 순서는 아래 예시와 정확히 일치해야 한다. 각 단계는 해당 표를 정확히 한 번 포함해야 한다. 재리뷰는 수정 확인 표와 새 지적 표를 각각 한 번 포함하며, 두 표의 순서는 상관없다. 기대하지 않은 머리글의 표, 중복 표, 필수 표 누락은 오류다. 표 밖 설명 문장은 무시한다.

각 행은 `|`로 시작하고 끝낸다. 셀은 한 줄, 셀 안의 `|`는 `\|`. 번호 중복·누락·모르는 번호·열거값 위반·빈 셀은 오류다. 초기 지적 0건은 머리글과 구분자만 있는 표다. 빈 응답이나 설명만 있는 응답은 오류다. 파싱 오류가 있으면 부분 결과를 채택하지 않고 상태를 그대로 보존한다.

지적 표:

```text
| 번호 | 심각도 | 파일:줄 | 재현 시나리오 | 확신도 |
| --- | --- | --- | --- | --- |
| 1 | high | head:internal/example.go:42 | 조건 → 동작 → 실제와 기대 | high |
```

작성자 응답 표 (`ACCEPT` 또는 `REJECT`):

```text
| 번호 | 응답 | 근거 |
| --- | --- | --- |
| r1-1 | ACCEPT | 수정할 동작 |
```

반박 검토 표 (`MAINTAIN` 또는 `WITHDRAW`):

```text
| 번호 | 판정 | 근거 |
| --- | --- | --- |
| r1-1 | MAINTAIN | 해소되지 않은 조건 |
```

수정 확인 표 (`FIXED` 또는 `UNFIXED`, 재리뷰 응답에는 새 지적 표도 필수):

```text
| 번호 | 확인 | 근거 |
| --- | --- | --- |
| r1-1 | FIXED | 새 SHA에서 확인한 수정 |
```

- 심각도: `critical` | `high` | `medium` | `low`. 확신도: `high` | `medium` | `low`.
- 파일:줄: `head:<경로>:<줄>` 또는 `base:<경로>:<줄>`(삭제된 줄). 경로는 저장소 상대 경로.
- 번호는 리뷰어가 `1, 2, …`로 쓰고 서버가 `r<라운드>-<번호>` ID를 붙인다. 이후 표는 서버 ID를 쓴다.
- 항목 상태: `open` → (`accepted_pending` → `fixed`) | (`disputed` → `withdrawn` | 유지 시 `disputed`). UNFIXED는 `accepted_pending` 유지.

## 5. 병합과 재시작 복구 (Opus 소유: `work.go`)

1. 대기열 맨 앞 파트를 통합 worktree의 detached HEAD(`IntegrationSHA`)에서 `git merge --no-ff <SubmitSHA>`로 커밋한다. 충돌이면 `git merge --abort` 후 `blocked{conflict}`(충돌 파일 목록 포함).
2. verify 명령(`argv` 배열, shell 문자열 금지)을 제한 시간 안에 순서대로 실행한다. 실패·시간 초과면 `blocked{verify}`(출력 끝부분 포함).
3. 만든 커밋 SHA를 `work.merging = {part_id, submit_sha, before_sha, merge_sha}`로 저장한다.
4. `git update-ref refs/heads/<통합branch> <merge_sha> <before_sha>`로 compare-and-swap 갱신한다.
5. 파트를 `merged`로 바꾸고 `merging`을 비운다.

재시작 시 `merging`이 있으면 통합 branch 현재 값을 본다. `merge_sha`이면 병합 완료로 처리한다. `before_sha`이거나 둘 다 아니면 `blocked{restart}`로 바꾸고 사유를 표시한다.

worktree·branch 이름: 파트 `rt/<방ID>/<partID>`, 통합 `rt/<방ID>/integration`. worktree 폴더는 서버 데이터 폴더 아래(`<data>/worktrees/<방ID>/<partID>`)에 만들고 사용자 저장소 안에 두지 않는다. 이미 있는 경로·branch와 충돌하면 즉시 실패한다. 정리는 소유권이 확인된 자원만, 강제 삭제 없이 한다.

## 6. HTTP API · SSE

```text
POST  /api/rooms/{id}/work                          WorkSpec → WorkPlan   (write 방만, 계획이 이미 있으면 409)
PATCH /api/rooms/{id}/work                          {"merge_mode":"auto|confirm"}
POST  /api/rooms/{id}/work/parts/{pid}/submit
POST  /api/rooms/{id}/work/parts/{pid}/approve      {"submit_sha","integration_sha"}  불일치 409
POST  /api/rooms/{id}/work/parts/{pid}/retry        Block 해제 → Block.From 상태, Halted 해제
POST  /api/rooms/{id}/work/parts/{pid}/abandon
GET   /api/rooms/{id}/work/parts/{pid}/diff         → PartDiff
SSE   event "work"  data = WorkPlan 전체 JSON (Snapshot에도 "work" 필드)
```

`WorkSpec` JSON:

```json
{
  "goal": "…",
  "merge_mode": "confirm",
  "review_rounds": 3,
  "verify": [{"name": "test", "argv": ["go", "test", "./..."], "timeout_sec": 600}],
  "parts": [{"title": "…", "brief": "완료 조건", "scope": ["internal/room/"], "seat": "<좌석ID>", "reviewer": "<다른 공급사 좌석ID>"}]
}
```

메시지·턴 확장: `Message.Part`(`json:"part,omitempty"`), `Message.ReviewStep`(`json:"review_step,omitempty"`: `findings`|`author_reply`|`rebuttal`|`recheck`), `Turn.Part`(`json:"part,omitempty"`), `Turn.Reason`에 `part`·`review` 추가.
