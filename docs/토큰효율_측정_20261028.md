# 토큰 효율 개선 측정 (2026-10-28)

목표는 결과 품질을 유지하면서 roundtable 좌석의 입력 토큰을 줄이는 것이다. 후보마다 같은 과제를 기존 방식과 나란히 돌렸다. 입력·캐시·출력·호출 수·시간과 객관 품질 기준을 비교해 채택 여부를 정했다. 측정 도구는 `tools/token_ab/`에 있다.

## 1. 출발점: 비용이 어디서 나오나

### 오케스트레이터 실측
- 범위: 10-26 12시~10-28 00시 KST에 갱신된 방, 좌석 답 220턴.
- 입력 합계 837.5M 가운데 캐시 읽기가 811.3M(97%)이다. 출력은 3.9M이다.
- 턴 끝 문맥이 200k 이상인 88턴이 입력의 57%다.
- 입력이 10M 이상인 18턴이 입력의 38%다.

### Codex 세션 로그 분석 (`tools/token_ab/codex_rollout.py`)
Terra 리뷰 대응 세션(`01a17c7a…`)의 작업별 수치다.

| 작업 | 모델 호출 | 첫 호출 문맥 | 마지막 호출 문맥 | 입력 합 |
|---|---:|---:|---:|---:|
| 0 | 91 | 113k | 184k | 14.6M |
| 1 | 122 | 189k | 243k | 26.4M |
| 2 | 134 | 245k | 328k | 39.4M |

이 표에서 비용 요인 세 가지가 보인다.
- 기반 세션 포크로 받은 문서 문맥(약 105k)이 모든 호출에 실린다.
- 작업이 바뀌어도 세션을 이어 쓰기 때문에 시작 문맥이 커진다.
- 작업마다 90~134회 호출한다.

가장 무거운 Codex 세션 12개를 호출 종류로 나누었다.
- 실행 중인 시험을 기다리는 빈 `write_stdin` 폴링이 입력의 18~45%를 차지했다.
- 폴링 430건 가운데 294건이 `yield_time_ms` 1000(1초)이었다.
- 어떤 지침도 1초를 지시하지 않았다. 모델의 습관이었다.

agy 무거운 방(`8a864d16ac29`)도 확인했다.
- `manage_task status`·`list` 호출이 1,186회 가운데 190회였다.
- agy의 `run_command` 도구 설명은 "백그라운드로 넘어간 명령은 끝나면 알림이 오니 폴링하지 말라"고 한다.
- `WaitMsBeforeAsync`의 상한은 10초다.

## 2. A/B 결과

공통 조건은 다음과 같다.
- 작업 사본은 roundtable `ac5988b`에 고정한 git worktree다.
- 좌석은 모두 effort high다.
- 시각은 10-28 00시~01시 KST다(서버 1fcd585·ac5988b 운영 중).
- 한 조건당 1~2회만 돌렸으므로 모델 출력의 편차를 다 덮지 못한다.

### T2. 인계 후 새 세션 — 채택 (`d1f6ca7`, `rt handoff`)

**준비**
- Claude Sonnet 5.5 기반 세션에서 4턴 동안 코드를 읽어 문맥을 120k로 키웠다. 대상은 forward.go, postUser, workspace_lock.go, limit_hold.go, hub.go 턴 생명주기, requests·prompt·store다.
- 작업 사본에 "리팩터링" 커밋 하나를 올렸다. 이름 바꾸기 같은 무해한 변경과 결함 3개가 섞여 있다.
  - D1 forward.go: 메모 300자 한도를 바이트로 셈.
  - D2 workspace_lock.go: Windows 경로의 대소문자를 맞추지 않음.
  - D3 limit_hold.go: 단위 뒤 숫자를 초로 다시 더함.
- 기존 시험이 잡는 결함은 D3 하나다.

**절차**
- A쪽은 기반 세션을 포크해 이어 썼다.
- B쪽은 기반 세션을 포크해 인계 요약을 받았다. 그다음 새 세션에 요약과 요청만 넣었다.
- 두 쪽 모두 턴 3은 검수, 턴 4는 수정+반례 시험+`go test`다.

| 쪽 | 입력 | 캐시 | 비캐시 | 출력 | 시간 |
|---|---:|---:|---:|---:|---:|
| A 이어쓰기(턴 3+4) | 1,554,538 | 1,403,407 | 151,131 | 11,890 | 4.6분 |
| B 인계(인계 턴+턴 3+4) | 885,000 | 832,918 | 52,005 | 10,876 | 6.7분 |

- 입력은 -43%, 비캐시 입력은 -66%다.
- 마지막 호출 문맥은 A 135k, B 47k다.
- 품질은 두 쪽이 같았다.
  - 검수에서 결함 3/3을 찾았고 오탐은 없었다.
  - 숨긴 시험 3개를 통과했다.
  - `internal/room` 전체 시험을 통과했다.
  - 좌석이 추가한 반례 시험은 결함 코드에서 3개 결함을 모두 잡았다.
- 시간이 늘어난 이유: B는 인계 턴(0.4분)이 더해졌고, 검수 턴에서 전체 시험을 돌렸다.
- 미검증
  - 실제 운영 방은 200~450k다. 이번 120k보다 절감 폭이 클 것으로 보이지만 추정이다.
  - Codex·agy 좌석의 인계는 돌리지 않았다.
  - 기반을 다시 포크하는 경로(`fresh` 없음)는 단위 시험으로만 확인했다.

### T3. CLI 자동 압축 기준 — 방 설정으로 채택, 기본은 끔 (`bd72027`)

**설정 확인**
- Codex: `-c model_auto_compact_token_limit`.
- Claude: `CLAUDE_CODE_AUTO_COMPACT_WINDOW`, `CLAUDE_AUTOCOMPACT_PCT_OVERRIDE`.
- agy: `AUTO_COMPACT_OVERRIDE`.
- 세 가지 모두 실행 파일 문자열에서 이름만 확인했다.

**절차**
- Claude CLI를 직접 실행해, 같은 120k 기반 세션을 포크한 검수+수정+시험 한 턴을 비교했다.
- B쪽만 `CLAUDE_CODE_AUTO_COMPACT_WINDOW=150000`이다.

| 쪽 | 입력 | 캐시 읽기 | 출력 | 압축 | 첫/마지막 호출 문맥 | 시간 |
|---|---:|---:|---:|---:|---|---:|
| A 기본 | 1,728,068 | 1,571,594 | 9,348 | 0 | 149k / 165k | 4.9분 |
| B 150k 창 | 1,066,700 | 996,780 | 8,331 | 1 | 78k / 97k | 7.7분 |

- 입력은 -38%다. B는 첫 호출 전에 한 번 압축했다.
- 품질은 두 쪽이 같았다. 결함 3/3 발견·수정, 숨긴 시험, 전체 시험, 반례 시험의 결함 검출 모두 같다.
- 시간은 +57%다. 그래서 기본값은 끄고 방마다 켜게 했다. 설정은 `rt update_room --compact_window_tokens 150000`이다.
- 미검증
  - 턴 도중 여러 번 압축되는 긴 작성 턴은 확인하지 않았다.
  - Codex·agy 압축 설정은 A/B를 하지 않았다. Codex 주간 잔여(약 26%)를 아끼려는 것이다.

## 3. 채택하지 않았거나 하지 않은 것

| 후보 | 결정 | 이유 |
|---|---|---|
| agy 대기 규칙 | 버림 | 두 번의 A/B에서 규칙 없는 쪽도 폴링이 0~1회였다. 효과를 보일 수 없었다. |
| Codex·agy 자동 압축 | 하지 않음 | 설정 이름만 확인했다. 사용량 제약(Codex 주간 잔여 약 26%)으로 A/B를 하지 않았다. |
| 작성·검수 템플릿에 파일:줄·시험 명령을 미리 넣기, 검수에 diff만 주기 | 하지 않음 | 품질 측정에 반복 실행이 많이 필요하다. 검수 템플릿의 변형 실행·반복 실행 요구는 호출을 늘리지만 품질을 위한 것이라 줄이지 않았다. |
