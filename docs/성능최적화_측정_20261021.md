### 조사 후 유지한 경로

참가자별 독립 큐·멘션·steering·작업/리뷰·MCP·첨부·CLI 열기·취소/재시작은 기존 호출 경로와 정책을 유지한다. `internal/server`의 SSE 연결·snapshot·trace API, `internal/rtmcp`의 공유 SSE observer와 대기/취소 경로도 확인했으며 새 네트워크 계층이나 대기열을 도입하지 않았다. 디스크 쓰기와 append lock도 그대로다.

`docs/토큰절감_측정_20261020.md`와 `tools/token_ab/`를 대조했다. 좌석별 미전달 메시지만 전달, 성공 시에만 커서 확정, 안내문 재사용·압축 후 재전송, 추론 수준 변경 시 세션 유지, Codex `features.plugins=false`, agy stdin 입력, 공급사별 턴 사용량 보정이 이미 구현돼 있다. 이 정책을 중복 구현하거나 세션·도구 맥락을 축소하지 않았다. 추가 토큰·비용 절감률은 **미측정**이다. 공급사 캐시 편차가 큰 기존 실험을 이번 코드의 성과로 합산하지 않는다.

README와 2026-10-18 자원 관리 기록의 “각 기록 200개 제한”은 실제 main과 달랐다. 실제로는 처음 열 때 최근 200개와 필요한 부모 문맥을 읽고, 이후 SSE를 계속 누적하며 요청 시 전체 기록을 불러온다. 이번 변경은 이 동작을 유지한다. README를 현재 코드에 맞게 정정했으며 과거 문서를 새 제한의 근거로 사용하지 않는다.

### pprof 보조 확인

32명 동시 턴을 별도로 30회 실행해 CPU와 alloc_space를 수집했다. 이 프로파일에는 benchmark 준비 비용도 포함되므로 위 B/op와 직접 나누어 비교하지 않는다. 표본 추정인 alloc_space에서 `roomState.broadcast`의 누적 할당은 267.64 → 114.05MB였고, CPU 표본 총량은 3.50 → 2.65초였다. 반복 직렬화 비용이 줄어든 방향과 일치한다. 이후에도 syscall·동기식 디스크 쓰기·lock 비용은 남아 있다. 단일 프로파일의 백분율을 반복 성능 효과로 제시하지 않는다.

작은 `pprof -top` 출력만 [cpu 전](../tools/perf/results/cpu-top-before.txt)·[후](../tools/perf/results/cpu-top-after.txt), [할당 전](../tools/perf/results/alloc-top-before.txt)·[후](../tools/perf/results/alloc-top-after.txt)로 저장했다. 큰 프로파일 바이너리는 커밋하지 않았고 재생성 명령은 재현 문서에 있다.

## 남은 한계·호환성

- 제품은 Go 단일 바이너리와 프레임워크 없는 정적 UI를 유지한다. 새로운 런타임 의존성이 없다. JSONL·API·SSE 필드/순서·권한/샌드박스·프롬프트·세션 의미를 바꾸지 않는다.
- read callback은 빌린 slice를 반환 이후 보관하면 안 된다. 현재 production callback은 모두 내부에서 JSON을 해석하고 값만 보관한다. 향후 소비자 추가 시 이 수명 계약을 지켜야 한다.
- 이벤트 switch에 participant 필드를 새로 변경하는 코드를 추가하면 갱신 조건도 함께 검토해야 한다. 현재 상태·세션·usage와 별도 setter 경로는 회귀 검사로 확인했다.
- 서버의 메시지 본문과 디스크 JSONL은 계속 누적된다. 전체 trace 열기·내보내기·진행 요약 복원의 전체 trace 읽기 비용도 남는다. 아주 큰 단일 행은 행 크기에 비례한 임시 메모리가 필요하다.
- trace의 신규 수신 복사를 줄였지만 전체 trace 렌더 자체를 가상화하지 않았다. 기록을 버려서 메모리를 제한하지 않는다. 최근 기록 조회는 여전히 파일 크기에 비례한다.
- pooled reader의 작은 idle heap 증가를 수용했다. 수시간/수일 실제 공급사 CLI 운용, Windows 실행, 모델 캐시·토큰/비용, 프레임 지연은 **미측정**이다. 짧은 합성 반복에서 누수가 없었다는 결과를 무기한 자원 상한으로 해석하지 않는다.
- 타임아웃·비정상 중단·재시작 복구의 기존 Go 테스트는 통과했지만 실제 프로세스 smoke의 재시작은 정상 종료였다. 실제 공급사 장애나 전원 차단 복구를 추가 실험하지 않았다.
